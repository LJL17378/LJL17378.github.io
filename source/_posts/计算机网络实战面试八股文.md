这篇文章不按“名词解释大全”组织，而是围绕一个工程师真正会遇到的问题展开：**浏览器访问一个 HTTPS 接口时，数据究竟经过了什么；失败时，怎样用证据判断坏在哪一层。**

你不需要先读另一篇教材。DNS、IP、端口、TCP、TLS、HTTP、代理等概念第一次出现时都会解释；每个章节都给出场景、机制、验证方法和面试表达。读完后应能独立回答网络八股，也能处理“域名能解析但接口超时”“浏览器报 CORS、curl 却正常”“502 与 504 怎么定位”这类实际问题。

## 一、先建立完整地图

### 1. 一次 HTTPS 请求到底经过哪些步骤？

以浏览器请求 `https://api.example.com/transactions` 为例：

1. 浏览器解析 URL。`https` 是协议，`api.example.com` 是域名，`/transactions` 是资源路径；未写端口时 HTTPS 默认使用 443。
2. 浏览器通过 DNS 把域名查询成 IP 地址。域名方便人记忆，IP 地址才用于在网络中寻找目标机器。
3. 客户端与目标 IP、端口建立传输连接。HTTP/1.1 和 HTTP/2 通常使用 TCP；HTTP/3 使用基于 UDP 的 QUIC。
4. HTTPS 还要完成 TLS 握手：验证服务器证书、协商加密算法和会话密钥。
5. 浏览器发送 HTTP 请求，包括方法、路径、请求头和可选请求体。
6. 请求可能先到 CDN、负载均衡或反向代理，再进入应用服务；应用可能访问 Redis、数据库或外部模型服务。
7. 响应沿链路返回。浏览器根据状态码、响应头和响应体决定展示、缓存或报错。

这也是排障顺序：**URL → DNS → IP 路由 → 端口/TCP → TLS → HTTP → 代理 → 应用 → 数据库。** 不要一看到“请求失败”就重启服务，因为失败可能发生在任何一层。

### 2. IP 地址和端口分别在找什么？

IP 地址用于找到一台网络接口所在的主机或网络位置；端口用于找到这台主机上的某个进程。可以把 IP 想成办公楼地址，端口是楼里的房间号。

`203.0.113.10:443` 表示连接这台主机的 443 端口。服务器程序必须在某个本地地址和端口上 **listen（监听）**，客户端才能连接。监听 `127.0.0.1:8000` 只接受本机请求；监听 `0.0.0.0:8000` 表示接受到达本机各 IPv4 网络接口的请求，但外部能否到达仍取决于防火墙、路由和云安全组。

面试中若被问“服务启动了为什么外部访问不了”，应依次检查：进程是否存活、监听的是哪个地址和端口、本机能否访问、主机防火墙和安全组是否放行、上游代理是否转发到正确地址。

### 3. MAC 地址、IP 地址和域名为什么同时存在？

域名解决人类可读性，IP 解决跨网络路由，MAC 地址解决本地链路的一跳交付。浏览器先把域名解析为 IP；若目标不在本地网段，主机把数据交给默认网关，并通过 ARP 查到网关的 MAC 地址，再封装成以太网帧发送。

数据每经过一个路由器，链路层的源/目标 MAC 通常会改变；在没有 NAT 的情况下，IP 层的源/目标地址用于端到端路由，通常保持不变。把三者混为一谈会导致错误回答：路由器不是根据远端服务器 MAC 在互联网中转发，DNS 也不是把域名直接变成 MAC。

### 4. 网络排障最通用的方法是什么？

先定义故障范围，再沿层次收集证据：

- 只有一个用户失败，还是所有用户？只有一个域名，还是所有网络请求？
- 是完全连不上、偶尔失败、首包慢，还是下载速度慢？从什么时候开始，是否与发布、证书更新或流量变化相关？
- DNS 能否得到预期 IP？到该 IP 是否有路由？端口能否建立连接？TLS 是否成功？HTTP 返回什么？应用日志是否收到请求？

每一步都应形成一个可验证假设。例如 `curl` 直接访问 IP 成功、访问域名失败，优先检查 DNS；TCP 能连但 TLS 握手失败，重点检查证书、SNI 和协议版本；HTTP 已返回 500，就不要继续把问题归咎于“三次握手”。

## 二、DNS：域名为什么会解析错

### 5. DNS 查询的完整过程是什么？

DNS（Domain Name System）把域名映射到 IP 等资源记录。浏览器先查自身缓存，操作系统再查本地缓存和 hosts 文件；没有结果时，请求配置的递归解析器，例如运营商或公共 DNS。

递归解析器若没有缓存，会依次询问根服务器、顶级域服务器和目标域的权威 DNS：根告诉它 `.com` 去哪里问，`.com` 告诉它 `example.com` 的权威服务器，权威服务器最终给出 A、AAAA 或 CNAME 等记录。回答带有 TTL，表示缓存可使用多久。

实际排障可用：

```bash
dig api.example.com
dig api.example.com A
dig api.example.com AAAA
dig @8.8.8.8 api.example.com
dig +trace api.example.com
```

默认查询看当前解析器结果；指定解析器可比较是否只有某个 DNS 缓存错误；`+trace` 展示从根到权威服务器的迭代路径。

### 6. A、AAAA、CNAME、NS、MX 和 TXT 记录是什么？

- A：域名指向 IPv4 地址。
- AAAA：域名指向 IPv6 地址。
- CNAME：把一个名字声明为另一个规范名字的别名，解析时还要继续查询目标。
- NS：声明某个 DNS 区域由哪些权威服务器负责。
- MX：声明邮件服务器，并带优先级。
- TXT：保存文本型验证或策略信息，常用于域名所有权验证、SPF 等。

面试常追问“为什么改了 CNAME 还没生效”：旧记录可能仍在各级递归解析器和客户端缓存中，直到 TTL 到期；还可能是改错 DNS 区域、权威服务器尚未同步，或客户端优先命中了 AAAA 而你只检查了 A。

### 7. 递归 DNS 和权威 DNS 有什么区别？

递归解析器代表客户端到处询问，并缓存答案；权威 DNS 保存某个区域的最终配置，是这个域名数据的来源。公司在云 DNS 控制台配置 A/CNAME，改的是权威数据；用户电脑通常询问的是递归解析器。

`dig` 输出中的 `SERVER` 常是本次询问的递归服务器，不一定是域名权威服务器。要找权威服务器可以查询 NS，再直接指定其中一个进行查询。理解这一区别，才能判断“配置已经正确但用户仍看到旧 IP”究竟是权威配置问题还是递归缓存问题。

### 8. TTL 越短越好吗？

TTL 短意味着变更后旧缓存更快过期，适合迁移前降低 TTL；代价是递归查询更多、权威 DNS 压力和解析延迟增加。TTL 长能提高缓存命中和稳定性，但故障切换或迁移传播更慢。

正确迁移流程通常是：提前至少一个旧 TTL 周期降低 TTL → 等旧缓存自然过期 → 切换记录 → 验证各地解析 → 稳定后再调高 TTL。事故发生后才把 TTL 从一天改为一分钟，已经缓存的一天记录不会因此立刻消失。

### 9. 域名能解析，但为什么仍访问不了？

DNS 成功只证明拿到了一个地址，不证明该地址有可达路由、端口开放、证书正确或应用健康。下一步应检查：

```bash
curl -v --connect-timeout 3 https://api.example.com/health
nc -vz api.example.com 443
openssl s_client -connect api.example.com:443 -servername api.example.com
```

`nc` 只验证能否建立到端口的 TCP 连接；`openssl s_client` 进一步观察 TLS 证书和握手；`curl -v` 能展示解析、连接、TLS 和 HTTP 的关键阶段。若域名有多个 A/AAAA 记录，还应分别测试，因为可能只有某个实例或 IPv6 路径故障。

## 三、TCP：连接、可靠性与线上状态

### 10. TCP 和 UDP 的核心区别是什么？

TCP 是面向连接的可靠有序字节流。它用序列号、确认、重传、滑动窗口和拥塞控制，让应用按顺序读到完整字节；但不保留应用消息边界。UDP 按数据报发送，保留每次发送的边界，却不承诺到达、顺序或去重。

DNS 查询、实时音视频可能使用 UDP，以较小状态和可控延迟换取应用自己处理丢失；HTTP/3 的 QUIC 也基于 UDP，但 QUIC 在用户态重新实现了连接、可靠性、拥塞控制和多路流。因此“UDP 不可靠”只描述 UDP 本身，不代表基于 UDP 的应用协议不能可靠。

### 11. TCP 为什么需要三次握手？

握手要让双方确认双向通信能力并同步初始序列号：客户端发 SYN 和自己的初始序列号 x；服务端回 SYN+ACK，确认 x，同时给出自己的序列号 y；客户端再回 ACK 确认 y。

第三次让服务端知道“客户端确实收到了服务端的序列号和连接响应”。如果只有两次，服务端无法区分自己的响应是否到达，也更容易因网络中迟到的旧 SYN 建立错误连接状态。

抓包时会看到 `SYN → SYN,ACK → ACK`。若大量停在 SYN-SENT，可能是请求发出但没有回应；大量 SYN-RECV 可能是客户端最后 ACK 未到、网络异常或 SYN flood，需要结合队列、来源和防火墙判断。

### 12. TCP 如何保证可靠传输？

TCP 给每个字节编号。接收方用 ACK 告诉发送方“下一个期望的字节序号”，发送方保留尚未确认的数据；超时或收到足够重复 ACK 时重传。校验和发现传输损坏，接收端按序列号重组乱序段并丢弃重复内容。

滑动窗口允许发送方在等 ACK 时继续发送一定数量的数据，避免“发一个等一个”的低吞吐。接收窗口保护接收方不被灌满，拥塞窗口保护网络不被发送方压垮，实际发送量受两者共同限制。

TCP 的可靠只覆盖字节流。例如客户端发 POST 后连接断开，它不知道服务端是否已经写库；业务层仍需要查询状态、业务唯一号或幂等键，不能把 TCP 可靠等同于“业务恰好执行一次”。

### 13. TCP 粘包和拆包是什么？

TCP 没有“消息”概念，只有连续字节流。发送方两次 `write`，接收方可能一次 `read` 全读到，也可能分三次读到。这不是 TCP 出错，而是应用错误地假设一次读取等于一条消息。

应用协议必须自己定义边界：固定长度、特殊分隔符、长度前缀，或像 HTTP 那样通过头部和帧结构描述长度。使用分隔符时要考虑内容转义；使用长度前缀时要限制最大长度，防止恶意长度导致内存分配攻击。

### 14. 四次挥手和 TIME_WAIT 为什么存在？

TCP 是全双工：一方发 FIN 只表示“我不再发送”，对方仍可能继续发送剩余数据，所以两个方向分别关闭，通常表现为 FIN、ACK、FIN、ACK 四段。若接收 FIN 后正好也没有数据要发，ACK 和 FIN 可以合并。

主动关闭方最后进入 TIME_WAIT。一方面，如果最后 ACK 丢失，它还能收到对方重传的 FIN 并再次确认；另一方面，让旧连接中迟到的数据包在网络中消失，避免污染相同四元组的新连接。

大量 TIME_WAIT 不一定是故障，它说明本机主动关闭了许多连接。应先检查是否频繁创建短连接、是否能使用连接池/Keep-Alive、端口范围是否耗尽，而不是粗暴关闭 TCP 的安全机制。

### 15. CLOSE_WAIT 很多意味着什么？

CLOSE_WAIT 表示本机已经收到对方 FIN，内核也通知了应用，但应用还没有关闭自己的 socket。少量短暂存在正常；持续大量堆积通常意味着代码没有执行 `close`，请求处理被卡住，或连接清理路径遗漏。

使用 `ss -antp state close-wait` 找到进程和对端，再结合线程栈、连接池、异常日志检查是谁持有连接。它和 TIME_WAIT 的责任方向不同：TIME_WAIT 常在主动关闭方，CLOSE_WAIT 堆积更应怀疑本机应用没有完成关闭。

### 16. Connection refused、timeout、reset 分别说明什么？

- `Connection refused`：目标主机明确回 RST，常见于目标地址可达但端口无人监听，或防火墙主动拒绝。
- `Connection timed out`：一定时间内没有得到预期响应，可能是路由黑洞、防火墙丢弃、服务严重拥塞，也可能超时发生在后续读取阶段。
- `Connection reset by peer`：已经存在的连接被对端或中间设备用 RST 异常终止，常见于进程崩溃、协议不符合、代理超时或对端强制关闭。

错误文字只给方向，不能替代证据。用 `curl -v` 区分 connect timeout 与 read timeout；用 `ss` 看本地状态；必要时用 `tcpdump` 确认是否发出 SYN、收到 RST 或发生重传。

### 17. 为什么延迟高但带宽没跑满？

带宽是单位时间最多能传多少数据，延迟是一个数据往返需要多久。高带宽高延迟链路需要较大的“在途数据量”才能跑满，这个量近似带宽与 RTT 的乘积，称为带宽时延积。

如果 TCP 窗口太小、丢包导致拥塞窗口下降，或应用一次只发很小请求再等待响应，即使线路标称 1Gbps 也跑不满。排查时分别测 RTT、丢包、吞吐和应用并发，不能用一次 `ping` 的低延迟证明下载一定快，也不能用测速带宽证明 API 一定快。

## 四、TLS 与 HTTPS：能连接不等于能安全通信

### 18. TLS 握手做了什么？

TLS 提供三件事：加密避免旁观者直接读取内容；完整性校验让篡改可被发现；证书验证服务器身份。TLS 1.3 握手中，客户端发送支持的版本、密码套件、随机参数和密钥交换信息；服务端选择参数、发送证书并证明持有对应私钥；客户端验证证书，双方导出对称会话密钥，之后用对称加密传输 HTTP。

非对称密码主要用于身份和密钥协商，对称加密负责大量数据，因为后者更快。HTTPS 不能防 SQL 注入、越权或 XSS，它保护的是传输链路，不会自动修复应用业务漏洞。

### 19. 浏览器如何验证证书？

证书把域名与公钥绑定，并由 CA 签名。浏览器检查：证书链能否追溯到本地信任的根 CA、域名是否在证书的 SAN 中、当前时间是否在有效期内、签名是否正确，以及必要的吊销信息。

常见故障包括证书过期、只覆盖 `example.com` 却访问 `api.example.com`、中间证书漏配、机器时钟错误，以及代理返回了错误站点的证书。验证可用：

```bash
openssl s_client -connect api.example.com:443 -servername api.example.com -showcerts
curl -Iv https://api.example.com
```

`-servername` 发送 SNI，使一台 IP 上托管多个 HTTPS 域名时，服务器能选择正确证书。

### 20. 为什么直接访问 IP 正常，访问域名却证书错误？

HTTPS 验证的是 URL 中的主机名是否被证书覆盖，不是“这个 IP 能否连通”。同一 IP 可能承载多个域名，TLS 握手中的 SNI 告诉服务器客户端想访问哪个域名；直接用 IP 时，SNI 和证书域名都可能不匹配。

排障时不要通过关闭证书校验把问题“修好”。若想把某域名临时指向指定 IP 并保持正确 Host/SNI，可使用 `curl --resolve api.example.com:443:203.0.113.10 https://api.example.com/`。这能绕过 DNS 进行定位，同时保留正确的域名语义。

### 21. TLS 成功但接口仍失败，说明什么？

只说明到该终点的加密会话建立成功。后面仍可能发生 HTTP 认证失败、路由不存在、反向代理找不到上游、应用异常、数据库超时等问题。

应继续查看 HTTP 状态码、响应头、request ID 和服务端日志。分层排障的价值就在这里：TLS 成功可暂时排除证书与握手问题，把范围收窄到 HTTP 及其后端链路。

## 五、HTTP：请求成功、缓存和版本差异

### 22. 一个 HTTP 请求和响应包含什么？

请求包含方法、目标路径、协议版本/帧、请求头和可选请求体。例如 `GET /transactions` 表示读取资源；`Content-Type` 描述请求体格式；`Authorization` 携带凭证。响应包含状态码、响应头和可选响应体。

HTTP 被称为无状态协议，是说每个请求的语义可独立理解，不代表应用不能有登录状态。Session、Cookie 或 Token 在请求中携带身份关联，使服务端把多个请求视为同一用户会话。

### 23. 200、201、204、301、304、400、401、403、404、409、429、500、502、503、504 如何区分？

| 状态码 | 含义 | 实战定位 |
| --- | --- | --- |
| 200 | 请求成功并有正常响应 | 查看响应体是否符合契约 |
| 201 | 资源已创建 | 常配合新资源 ID 或 Location |
| 204 | 成功但没有响应体 | 客户端不要再解析 JSON |
| 301/308 | 永久重定向 | 检查跳转地址和缓存影响 |
| 304 | 缓存内容未修改 | 使用本地缓存，不含完整响应体 |
| 400 | 请求格式或参数有误 | 修正请求，原样重试无效 |
| 401 | 缺少有效身份凭证 | 登录或刷新 Token |
| 403 | 身份已知但无权限 | 检查授权与资源归属 |
| 404 | 资源/路由不存在 | 检查路径、ID 和部署版本 |
| 409 | 与当前资源状态冲突 | 处理版本、重复或并发冲突 |
| 429 | 频率或配额超限 | 按 Retry-After 退避 |
| 500 | 当前应用出现未预期错误 | 用 request ID 查应用日志 |
| 502 | 代理收到上游无效响应 | 查代理到上游的连接、协议、崩溃 |
| 503 | 服务暂时不可用 | 查过载、维护、就绪检查和熔断 |
| 504 | 代理等待上游超时 | 查上游耗时、超时层级和队列 |

`502/503/504` 都可能由网关返回，但含义不同：502 是上游响应无效或连接异常，503 是当前没有可服务能力，504 是等太久。定位时必须知道这个状态码由哪一层生成。

### 24. HTTP/1.1、HTTP/2 和 HTTP/3 的主线区别是什么？

HTTP/1.1 支持持久连接，但浏览器常需开多个 TCP 连接提高并发；同一连接上的请求响应组织能力有限。HTTP/2 把消息拆成二进制帧，在一个 TCP 连接中多路复用多个流，并压缩头部。

HTTP/2 多个流仍共享同一 TCP 字节流。一旦底层 TCP 丢包，后续字节要等缺口重传，所有流可能受到传输层队头阻塞。HTTP/3 使用 QUIC，把独立流的可靠性放到 QUIC 层，一个流丢包通常不阻塞其他流交付；QUIC 还整合 TLS 1.3，并支持连接迁移。

三者的 HTTP 方法、状态码和核心语义一致。升级协议不会自动优化慢 SQL，也不会消除应用队列和服务器处理时间。

### 25. Keep-Alive 和连接池解决什么问题？

建立 TCP 和 TLS 连接有握手成本。HTTP 持久连接允许多个请求复用已有连接；客户端连接池维护有限数量的可复用连接，避免每次请求重新握手，也防止无限创建连接压垮双方。

连接池太小会让请求排队，太大则让服务端连接数、内存和数据库下游承受更高并发。还要设置连接建立超时、读取超时、空闲连接寿命和最大连接寿命，避免复用已经被代理或服务端关闭的陈旧连接。

### 26. HTTP 缓存如何工作？

缓存先区分私有缓存与共享缓存：浏览器缓存只服务一个用户；CDN/代理缓存可能服务很多用户，不能错误共享个性化账单响应。

`Cache-Control: max-age=3600` 表示一小时内响应新鲜，可直接复用；`no-store` 表示不应存储；`no-cache` 不是“不缓存”，而是复用前必须向源站验证。过期后可带 `If-None-Match` 和 ETag，或 `If-Modified-Since` 与 Last-Modified 做条件请求；未变化时服务端回 304，节省响应体传输。

带内容哈希的 JS/CSS 文件适合 `public, max-age=31536000, immutable`；HTML 常需要较短缓存或重新验证；个性化接口要使用 `private` 或合适的禁止共享策略。若响应会随 `Accept-Encoding`、Origin 等请求头变化，要正确设置 `Vary`，否则共享缓存可能返回错误版本。

### 27. 为什么浏览器报 CORS，但 curl 正常？

CORS 是浏览器执行的跨源读取限制。源由协议、主机和端口共同决定；任一不同就是跨源。curl 和服务端程序不受浏览器同源策略限制，所以能成功并不能证明浏览器也允许页面 JavaScript 读取响应。

带自定义请求头、JSON Content-Type 或 DELETE 等请求时，浏览器可能先发 OPTIONS 预检，询问服务器是否允许这个 Origin、方法和请求头。排障要在 Network 面板先看 OPTIONS 是否成功，再看实际请求。允许 Cookie 时，`Access-Control-Allow-Origin` 不能使用 `*`，必须返回明确来源并配合 `Access-Control-Allow-Credentials: true`。

CORS 不是认证。攻击者可以绕过浏览器直接请求接口，因此服务端仍必须验证 Token、权限与资源归属。

### 28. connect timeout、read timeout 和总超时有什么区别？

连接超时限制建立 TCP/TLS 连接最多等多久；读取超时通常限制连接建立后，两次数据到达之间或等待响应的时间；总超时限制整个操作从开始到结束的最长时间。

只设置一个很长超时，会让失败请求长期占用线程、连接池和内存。多层系统还要让外层截止时间大于内层并留出处理余量，例如网关 5 秒、BFF 调下游 4 秒、下游模型 3 秒。否则内层还在工作，外层已经返回 504，浪费资源并可能产生未知写入结果。

### 29. 网络错误可以直接重试吗？

只对可能恢复的临时错误重试，例如连接建立失败、429、部分 502/503/504；参数错误、认证失败和确定的业务拒绝不应重试。使用指数退避和随机抖动，限制次数和总截止时间，避免故障时所有客户端同步重试形成流量风暴。

写操作必须先解决幂等。超时只表示客户端没收到结果，不代表服务端没执行；若直接重发“扣款 100 元”，可能扣两次。使用幂等键、业务唯一号、状态查询或条件更新，使重复请求留下同一结果。

## 六、代理、负载均衡与 CDN

### 30. 正向代理和反向代理有什么区别？

正向代理代表客户端访问外部网络，例如公司统一出网代理；目标服务看到的通常是代理。反向代理代表服务端接收外部请求，例如 Nginx 对外监听 443，再把请求转发到内网应用；客户端不需要知道真实后端实例。

反向代理常负责 TLS 终止、路由、静态文件、压缩、限流和负载均衡。排障时要明确每一跳：浏览器到 CDN、CDN 到网关、网关到应用分别可能有独立 DNS、连接池、超时和证书。

### 31. 四层和七层负载均衡有什么区别？

四层负载均衡根据 IP、端口和 TCP/UDP 连接转发，不理解具体 HTTP 路径，协议通用、处理开销较低。七层负载均衡理解 HTTP，可按域名、路径、Header、Cookie 路由，还能处理 TLS、缓存和应用级限流。

若 `/api` 与 `/static` 要转到不同服务，需要七层信息；若只是把大量 TCP 连接均匀分给后端，四层可能更合适。七层返回 502 时，说明它作为 HTTP 代理发现上游异常；四层设备通常无法生成同样的应用语义。

### 32. 负载均衡有哪些分配策略？

轮询适合能力接近、请求耗时相近的实例；加权轮询让高配置机器承担更多；最少连接适合长连接或请求耗时差异大；一致性哈希可让同一 Key 倾向同一实例，但需防热点与扩缩容影响。

健康检查必须区分存活与就绪：进程活着不代表已加载配置、连接数据库并能接流量。实例准备完成前就加入负载均衡，常造成发布期间短暂 502/503。

### 33. CDN 为什么能加速，又为什么会返回旧内容？

CDN 把可缓存响应放到靠近用户的边缘节点，减少网络距离、源站计算和出口带宽。第一次未命中时边缘节点回源获取并缓存，后续用户直接命中边缘。

旧内容通常来自缓存键、TTL 或刷新策略。若缓存键没有包含语言、设备或必要查询参数，不同请求可能错误共用结果；源站更新不会自动删除所有已有缓存，需等待过期、版本化 URL 或主动 purge。用户内容若被共享缓存，还可能造成严重数据泄露。

排查时比较 `Age`、`Cache-Control`、`ETag`、CDN 特有命中头，并分别请求 CDN 与源站。不要用强制刷新浏览器就断定 CDN 已更新，因为浏览器缓存和 CDN 缓存是两层。

### 34. X-Forwarded-For、X-Forwarded-Proto 和 Host 有什么用？

经过反向代理后，应用直接看到的 TCP 对端往往是代理，而不是用户。代理可用 `X-Forwarded-For` 传递原始客户端 IP，用 `X-Forwarded-Proto` 表示外部是 HTTP 还是 HTTPS，Host 表示用户访问的域名。

这些头可以被公网客户端伪造。应用只能信任由已知代理覆盖/追加的值，并配置可信代理列表；否则攻击者可能伪造 IP 绕过限流或审计。若应用误判外部协议，还可能生成错误的 HTTP 回调地址或产生重定向循环。

## 七、长连接、流式响应与实时通信

### 35. 轮询、长轮询、SSE 和 WebSocket 如何选择？

普通轮询每隔几秒请求一次，简单但有无效请求和延迟。长轮询让服务端在有事件或超时前暂不响应，返回后客户端立刻发下一次。SSE 使用一个 HTTP 响应持续发送文本事件，浏览器 `EventSource` 支持自动重连，适合通知、任务进度和 AI 文本流。

WebSocket 经 HTTP 握手升级后形成全双工帧通道，双方可随时发送文本或二进制，适合聊天、协作、游戏和实时控制。AI 问答通常是客户端发一次请求、服务端持续输出，SSE 往往更简单；若双方都要高频发送，再选择 WebSocket。

### 36. 长连接为什么在本地正常，上线后会断？

生产链路多了 CDN、网关、负载均衡和 NAT，它们常有空闲超时；若连接长时间没有字节经过，中间设备可能主动关闭。代理缓冲还可能把 SSE 内容攒起来，导致浏览器很久才一次看到。

需要配置正确的代理超时和关闭缓冲，定期发送心跳，并让客户端实现带退避的重连。重连后若不能丢事件，事件必须有 ID 和持久化来源；WebSocket/SSE 服务多实例部署时，还要让消息通过共享消息系统或正确路由到持有连接的实例。

### 37. 什么是背压？

背压是消费者速度低于生产者时，系统把“我处理不过来”的信号向上游传递。若模型每秒生成的数据远快于客户端网络，服务端无限缓存会耗尽内存。

解决方式包括有界队列、暂停上游读取、批量合并、降低生成速率、丢弃允许丢的进度事件，或超过上限后断开慢消费者。背压不是简单增加缓存；缓存只能吸收短暂波峰，不能解决长期速度不匹配。

## 八、Linux 实战工具：每个命令回答什么问题

### 38. ping 能证明服务正常吗？

不能。ping 使用 ICMP 测试目标主机与网络路径是否响应，并估计 RTT 和丢包；很多网络会限制 ICMP，而 HTTP 服务可能在 ping 正常时仍未监听端口、TLS 失败或应用返回 500。

ping 失败也不必然表示 HTTPS 不通。应把它当作一条证据，再用 DNS 查询、`nc`、`curl`、`ss` 等验证更高层。面试中说“先 ping，一通就说明网络没问题”是不严谨的。

### 39. curl、nc、ss、ip 分别用来做什么？

```bash
curl -v https://api.example.com/health
nc -vz api.example.com 443
ss -lntp
ss -antp
ip addr
ip route
```

`curl -v` 展示应用请求经过的解析、连接、TLS 和 HTTP 信息；`nc -vz` 快速探测目标 TCP 端口；`ss -lntp` 查看本机谁在监听 TCP 端口，`ss -antp` 查看连接状态和所属进程；`ip addr` 看本机地址，`ip route` 看路由表与默认网关。

工具应跟问题匹配：查“进程有没有监听”用 `ss`，查“请求返回什么”用 `curl`，查“发往该 IP 走哪条路由”用 `ip route get 目标IP`。不要堆命令而不解释每条命令要证伪什么假设。

### 40. traceroute 显示中间节点 `*`，是否表示那里断网？

traceroute 利用逐步增加 TTL，并观察中间路由器返回的 ICMP 超时消息来推断路径。某一跳显示 `*` 可能只是该设备不回复或限制 ICMP，后续跳仍出现就说明流量依然通过。

互联网路径还可能因负载均衡而变化，去程与回程也不一定相同。因此 traceroute 适合观察大致路径和在哪一段开始异常，不能仅凭一个星号断定某台路由器丢包。最终仍需结合终点连通、持续丢包、运营商和抓包证据。

### 41. tcpdump 抓包时应该看什么？

`tcpdump` 捕获经过网络接口的数据包。常用过滤示例：

```bash
sudo tcpdump -ni any host 203.0.113.10 and port 443
sudo tcpdump -ni eth0 'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0'
```

先看 SYN 是否发出、SYN-ACK 是否回来；再看 TLS/应用数据是否交换；异常时看重传、重复 ACK、RST、FIN 和长时间空白。HTTPS 内容被加密，抓包通常看不到 HTTP 正文，但仍能判断连接、方向、时间和包大小。

抓包应控制接口、主机、端口和时间范围，避免收集无关或敏感流量。生产环境抓包还要注意磁盘、性能和访问权限。

### 42. 如何判断丢包、网络慢还是应用慢？

先分解总耗时：DNS 时间、TCP connect、TLS、首字节时间（TTFB）和下载时间。curl 可以输出这些阶段：

```bash
curl -sS -o /dev/null \
  -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' \
  https://api.example.com/health
```

DNS 高说明解析链路慢；connect 高可能是网络、握手重传或服务端 SYN 队列；TLS 高检查证书链、CPU 和网络往返；TTFB 高但前面正常，重点看代理排队与应用处理；下载阶段高则关注带宽、响应体大小、拥塞和客户端消费速度。

抓包中的重传不一定全是网络物理丢包，也可能是接收方过载或抓包位置造成的观察误差。要把客户端时间、服务端 trace、代理指标和数据包时间线对齐。

## 九、高频实战场景题

### 43. 浏览器打不开接口，但服务器本机 curl 正常，怎么查？

先确认本机 curl 使用的是 `localhost` 还是公网域名。若只访问 `127.0.0.1:8000` 成功，说明应用进程正常，不代表外部链路正常。

检查服务是否监听 `0.0.0.0` 或正确网卡地址；主机防火墙、云安全组是否放行；反向代理是否监听公网端口并转发到正确上游；DNS 是否指向正确 IP；浏览器是否因 TLS、Mixed Content 或 CORS 阻止访问。按层验证，直到找到“上一层成功、下一层失败”的边界。

### 44. 接口偶发 502，应该怎样定位？

先确定 502 由 CDN、网关还是自建 Nginx 生成，从响应头、错误页面、日志和 request ID 判断。502 表示这个代理没拿到有效上游响应，常见原因有连接被拒绝、上游进程重启、连接提前关闭、协议/端口配错、响应头非法。

对齐同一时间的代理错误日志、应用重启记录、实例健康状态和连接指标；检查是否只发生在某一实例。若负载均衡轮询到坏实例，就会表现为“偶发”。修复后还应改进就绪检查和优雅关闭，避免发布时继续把流量发给退出中的实例。

### 45. 接口偶发 504，为什么不能只加大超时？

504 表示网关等待上游超过期限。加大超时可能让用户等更久，也让连接、线程、内存和数据库资源占用更久，最终把局部慢请求扩大为系统拥塞。

先用 trace 拆分排队、应用、SQL、Redis、外部 API 各阶段耗时，并看 P95/P99 而非平均值。明确外层与内层超时预算；能异步化的长任务改为提交任务并查询状态；对模型服务设置取消、并发上限和降级；只在业务确实允许更长等待且容量评估通过后调整超时。

### 46. 发布后短时间大量 503，可能是什么？

503 表示服务暂时没有能力处理。发布场景常见原因是新实例尚未加载完成就被标记就绪，旧实例又已经停止接流量；或实例收到终止信号后立即退出，正在处理的请求被中断。

应区分存活检查和就绪检查：加载配置、连接依赖完成后才就绪；关闭时先变为不就绪，从负载均衡摘除，再等待在途请求和长连接在期限内结束。还要检查容量是否在滚动发布期间下降过多，以及数据库迁移是否与新旧版本兼容。

### 47. 只有部分地区用户访问慢，怎么查？

优先怀疑地域相关的 DNS/CDN 调度、运营商互联、IPv6、边缘节点或跨地域回源。收集慢用户的地区、运营商、解析 IP、协议版本、时间分解和 traceroute，而不是只在办公室复现。

比较不同递归 DNS 的答案，检查是否某个边缘节点或源站异常；分别测试 A 与 AAAA，排除 IPv6 路径问题；查看 CDN 的命中率、回源延迟和分区错误率。必要时让 CDN/运营商结合时间与目标 IP 排查链路。

### 48. 页面首屏慢，网络层应该看什么？

先在浏览器 Network 面板区分：主文档 TTFB 慢、静态资源下载慢、资源数量过多，还是 JavaScript 下载后执行慢。TTFB 慢继续拆 DNS、connect、TLS、服务端处理；下载慢看资源体积、压缩、CDN 命中和协议；请求排队多看连接复用和优先级。

网络优化包括合理缓存与内容哈希、Brotli/gzip、图片格式和尺寸、CDN、减少关键路径请求、HTTP/2/3；但若资源很快下载完、主线程执行 3 秒，继续调 CDN 不会解决渲染瓶颈。

### 49. WebSocket 经常断线，如何设计重连？

先记录关闭码、连接时长、最后心跳和网络切换，判断是服务端主动关闭、代理空闲超时、移动网络变化还是进程发布。客户端重连要指数退避加随机抖动，并设置最大等待；立即无限重连会在服务恢复时制造风暴。

连接恢复不等于业务状态恢复。消息应有序列号或事件 ID，客户端告诉服务端“我最后收到哪条”，服务端补发或让客户端重新同步快照。发送操作要有业务 ID 防重复；服务端多实例需要共享消息层或连接路由策略。

### 50. 面试时怎样回答“线上网络故障你会怎么排查”？

一个成熟答案应按以下结构：

1. 先确认影响范围、时间、症状和最近变更，保护现场并决定是否回滚或降级。
2. 用一次真实请求沿 DNS、连接、TLS、HTTP、代理、应用逐层缩小范围。
3. 每层给证据：`dig` 的解析结果、`curl` 的时间分解、`ss` 的监听/连接状态、代理和应用的同一 trace、必要时的抓包。
4. 找到根因后修复，并验证用户指标恢复，而不是只验证某个命令成功。
5. 补上长期措施：监控、超时、健康检查、容量、自动化验证和事故复盘。

面试官真正关注的是你的推理顺序：你能否避免随机试错，能否区分现象、假设与证据，能否说明修复的副作用和验证方式。

## 十、面试前速记表

| 现象 | 第一批检查 | 常见方向 |
| --- | --- | --- |
| 域名不存在 | `dig`、权威 NS | 配置、记录类型、缓存、DNSSEC |
| 域名有 IP 但连不上 | `nc`、`curl -v`、路由 | 监听、防火墙、安全组、错误 IP |
| TLS 失败 | `openssl s_client`、证书时间和 SAN | 证书链、SNI、协议版本、时钟 |
| 浏览器失败 curl 正常 | Network 面板、OPTIONS | CORS、Mixed Content、Cookie、缓存 |
| 偶发 502 | 代理日志、实例维度 | 坏实例、重启、错误端口、提前关闭 |
| 504 | trace、耗时分解 | 慢 SQL、排队、下游超时、超时预算 |
| 大量 CLOSE_WAIT | `ss -antp`、线程栈 | 应用未关闭 socket |
| 大量 TIME_WAIT | 连接创建速率、池配置 | 短连接、主动关闭、端口压力 |
| SSE/WS 断线 | 代理超时、心跳、关闭码 | 空闲超时、发布、移动网络、无重连 |
| 部分地区慢 | 地域/运营商、DNS、CDN、IPv6 | 调度错误、坏边缘、跨网质量 |
