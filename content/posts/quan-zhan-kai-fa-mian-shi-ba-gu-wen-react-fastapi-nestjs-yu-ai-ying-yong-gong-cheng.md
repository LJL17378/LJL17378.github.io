这份手册服务于一条明确的技术主线：**React/TypeScript 负责前端，Python/FastAPI 负责 AI 应用后端，Node.js/NestJS 负责 BFF、CLI、MCP 与前端工程化。** 内容按常见题库补齐了语言运行时、框架原理、数据层、可靠性和 AI 工程追问，不只停留在项目介绍层面。

它不追求把所有后端语言都背一遍，而是帮助你回答三个问题：

1. 能不能独立完成一个前后端闭环？
2. 能不能把 AI Demo 做成可靠的在线服务？
3. 遇到并发、缓存、鉴权、失败和性能问题时，是否知道如何处理？

## 使用方法

每道题先记住“回答”里的主干，再理解“追问”。面试时建议按以下结构组织答案：

> 先给结论 → 解释原理 → 说明取舍 → 落到自己的项目。

例如回答“为什么使用 SSE”：

> 我的场景主要是服务端持续向浏览器推送模型输出，客户端很少在同一条连接上反向发送数据，因此 SSE 比 WebSocket 更简单，也能复用 HTTP 鉴权和网关。项目中我还处理了断线重连、心跳、取消生成和代理缓冲问题。如果要做实时协作或高频双向通信，我会改用 WebSocket。

## 一、全栈架构与接口设计

### 1. 什么是全栈开发？

**回答：** 全栈不是“每一层都会一点”，而是能围绕一个业务目标完成浏览器交互、接口设计、服务端逻辑、数据存储、部署和排障的闭环。真正重要的是理解各层边界：前端负责交互和展示，BFF 负责面向页面聚合，领域服务负责业务规则，数据库负责可靠存储，缓存和消息系统负责性能与解耦。

**项目表达：** 我的主线是 React/TypeScript + FastAPI。需要适配多个前端或聚合多个服务时，使用 NestJS 做 BFF；AI 推理、数据分析和 Agent 编排留在 Python 服务中。

### 2. 为什么不能把所有业务都写在前端或 BFF 中？

**回答：** 前端代码会下发到用户设备，不能保存密钥，也不能作为权限和金额等规则的可信边界。BFF 可以做协议转换、字段裁剪和接口聚合，但核心业务规则如果只存在于某一个 BFF，会导致多端逻辑不一致。鉴权最终校验、事务和领域规则应放在后端服务中。

### 3. 什么是 BFF？它解决什么问题？

**回答：** BFF 是 Backend for Frontend，为某一类前端提供定制接口。它可以聚合多个下游请求、裁剪字段、统一鉴权、转换协议，并减少前端与内部服务的耦合。

**代价：** 多了一层网络跳转和维护成本；如果把领域逻辑大量写进 BFF，会形成新的单体。BFF 应保持“面向体验的编排层”定位。

### 4. RESTful API 应该怎样设计？

**回答：** 用资源表达路径，用 HTTP 方法表达动作，例如 `GET /transactions`、`POST /transactions`、`PATCH /transactions/{id}`。状态码表达请求结果，请求体和响应体保持稳定结构，并统一分页、错误码、时间格式和字段命名。

常见状态码：

- `200` 查询或更新成功；`201` 创建成功；`204` 成功但无响应体。
- `400` 请求格式错误；`401` 未认证；`403` 已认证但无权限；`404` 资源不存在。
- `409` 状态冲突；`422` 语义或参数校验失败；`429` 请求过多。
- `500` 服务内部错误；`502/503/504` 通常与上游或服务可用性有关。

### 5. PUT 和 PATCH 有什么区别？

**回答：** PUT 通常表示用完整表示替换资源，PATCH 表示部分更新。PUT 在语义上应当幂等；PATCH 是否幂等取决于补丁定义，例如“将名称改为 A”是幂等的，“余额增加 10”不是。

### 6. 什么是幂等？如何实现？

**回答：** 同一个请求执行一次或多次，产生的最终业务结果相同。GET、PUT、DELETE 在 HTTP 语义上应当幂等，但具体实现仍需保证。

对创建订单、导入账单等操作，可以让客户端传 `Idempotency-Key`，服务端把键、用户、请求摘要和处理结果持久化。重复请求直接返回原结果。数据库唯一约束是最后防线，不能只依赖 Redis 锁。

### 7. 如何设计统一错误响应？

**回答：** 错误响应应包含稳定的业务错误码、可读信息、请求追踪 ID，以及必要的字段级错误；不要把堆栈和数据库细节暴露给客户端。

```json
{
  "code": "TRANSACTION_NOT_FOUND",
  "message": "账单不存在或无权访问",
  "requestId": "req_123",
  "details": []
}
```

HTTP 状态码给网关和通用客户端使用，业务错误码给产品逻辑和排障使用，两者不能互相替代。

### 8. 接口如何做分页？

**回答：** 数据量小、需要跳页时可用 `offset + limit`，实现简单，但深分页会扫描和丢弃大量记录，并且数据变动时可能重复或遗漏。信息流和大表更适合游标分页，以稳定排序字段加唯一 ID 作为游标，例如 `(created_at, id)`，查询下一页时使用范围条件。

### 9. 如何保证前后端类型一致？

**回答：** 以 OpenAPI 或 JSON Schema 作为接口契约，再生成 TypeScript 客户端和类型。Python 端用 Pydantic 校验，NestJS 端用 DTO 与运行时校验，前端不要把 TypeScript 类型误当成运行时校验。

版本变更优先做向后兼容：新增可选字段通常安全，删除字段、改类型或改语义需要版本管理和迁移窗口。

### 10. 一次请求在系统中经过哪些层？

**回答：** 常见链路是 CDN/负载均衡 → 网关或反向代理 → BFF/应用服务 → 缓存或数据库 → 外部模型服务。每层都可能增加超时和失败，因此要设置连接超时、读取超时、总截止时间和有限重试，并通过同一个 trace ID 串起日志。

### 11. API 如何做版本管理？

**回答：** 可在路径、请求头或媒体类型中表达版本。优先通过新增可选字段、容忍未知字段等方式保持向后兼容；必须破坏兼容时，再提供新版本和明确迁移窗口。版本不是永久复制整套代码，还要记录使用方、弃用日期和流量，确认旧客户端退出后再删除。

### 12. REST、GraphQL 和 gRPC 如何选择？

**回答：** REST 生态成熟、缓存和调试直观，适合公开资源 API；GraphQL 允许客户端按需取字段，适合页面组合复杂的产品，但要处理查询成本、N+1 和缓存；gRPC 基于强类型契约和 HTTP/2，适合内部服务高效通信，但浏览器直连和人工调试不如 REST 方便。选型取决于调用方与治理能力。

### 13. 如何设计文件上传接口？

**回答：** 小文件可由应用接收，但要限制大小、类型、数量和超时；大文件更适合客户端用预签名 URL 直传对象存储，应用只签发权限并保存元数据。需要断点续传时采用分片、校验和与完成合并流程。上传完成后还要做病毒扫描、内容嗅探、权限隔离和过期清理。

### 14. Webhook 怎样做到可靠和安全？

**回答：** 发送方用共享密钥对时间戳和原始请求体签名，接收方校验签名、时间窗口和事件 ID；接收后尽快持久化并返回，再异步处理。发送方采用指数退避和有限重试，接收方按事件 ID 幂等。还应支持密钥轮换、失败记录与人工补发。

### 15. 如何做接口限流？

**回答：** 先定义维度，如用户、IP、租户、模型或接口，再选择令牌桶、滑动窗口等算法。单机可在内存实现，多实例通常使用 Redis 或网关统一限制。超过限制返回 `429` 和合理的重试信息；内部还要限制并发、队列长度和单用户成本，防止慢请求耗尽资源。

### 16. 如何实现接口的乐观并发控制？

**回答：** 为资源维护版本号或更新时间，读取时返回 `ETag`，更新时要求客户端带 `If-Match`；服务端只在版本仍一致时更新，否则返回 `412` 或业务冲突。这样能防止两位用户互相覆盖修改，比“最后一次写入获胜”更可控。

### 17. API 网关和 BFF 的边界是什么？

**回答：** 网关处理跨业务的入口能力，如 TLS、路由、认证接入、限流和统一观测；BFF 面向某一客户端聚合数据、裁剪字段和适配交互。网关不应理解具体页面，BFF 也不应复制所有通用基础设施或承担核心领域事务。

### 18. 微服务一定优于单体吗？

**回答：** 微服务能独立部署和扩缩团队边界，但带来网络失败、数据一致性、链路追踪、版本治理和运维成本。业务和团队规模较小时，模块化单体通常更简单。拆分应基于明确的领域边界、独立扩展或交付需求，而不是为了技术名词。

## 二、Python 与 FastAPI

### 19. FastAPI 为什么性能较好？

**回答：** FastAPI 基于 ASGI，配合 Uvicorn 可以高效处理 I/O 并发；Starlette 提供 Web 能力，Pydantic 提供数据校验。性能主要来自异步 I/O 和较薄的框架层，而不是 Python 单线程突然变快。CPU 密集任务仍会阻塞事件循环，应交给进程池、任务队列或独立服务。

### 20. WSGI 和 ASGI 有什么区别？

**回答：** WSGI 面向同步请求响应模型；ASGI 支持异步调用、长连接和 WebSocket。传统 CRUD 用 WSGI 也可以，模型流式输出、并发访问外部 API 和 WebSocket 更适合 ASGI。

### 21. `async def` 一定比 `def` 快吗？

**回答：** 不一定。异步的优势是等待网络、数据库等 I/O 时把执行权交回事件循环，提高并发能力。CPU 计算不会因为 `async` 加速；在异步函数里调用阻塞库反而会卡住整个事件循环。

**追问：** FastAPI 可以在线程池中执行同步路由，但线程也有开销。应根据依赖库是否支持异步选择写法，不能机械地把函数全改成 `async`。

### 22. Python 事件循环如何工作？

**回答：** 协程运行到 `await` 且等待对象未完成时，会挂起并把控制权交给事件循环。事件循环监听 I/O 就绪事件，待结果可用后把协程放回可运行队列。它适合大量 I/O 并发，不等于多个 Python 字节码同时在多个 CPU 核心上执行。

### 23. GIL 是什么？

**回答：** 在常见 CPython 实现中，GIL 使同一进程内通常只有一个线程执行 Python 字节码。I/O 等待时会释放 GIL，所以线程仍适合 I/O 密集任务；纯 Python CPU 密集任务可使用多进程、原生扩展或独立计算服务。GIL 与数据库事务、协程安全是不同问题。

### 24. FastAPI 的依赖注入有什么用？

**回答：** `Depends` 可以声明并复用数据库会话、当前用户、权限检查和配置等依赖，还能处理请求结束后的资源清理。它让路由只关注用例，测试时也容易覆盖依赖。

### 25. Pydantic、SQLAlchemy 和 SQLModel 分别负责什么？

**回答：** Pydantic 负责输入输出的数据解析和校验；SQLAlchemy 是 ORM 与 SQL 工具；SQLModel 在两者之上提供更统一的模型写法。接口 DTO 和数据库实体最好仍保持边界，避免数据库字段无意中暴露到 API，也避免接口变化直接驱动表结构变化。

### 26. FastAPI 中间件和依赖项如何选择？

**回答：** 中间件适合对所有请求生效的横切逻辑，如 request ID、耗时、CORS 和通用日志。依赖项适合路由级且需要业务上下文的逻辑，如解析当前用户和权限。异常处理器负责把不同异常统一转换为响应。

### 27. 后台任务如何选择？

**回答：** FastAPI `BackgroundTasks` 适合发送日志、轻量通知等短任务，它与应用进程共存，没有可靠持久化。耗时、必须重试或不能丢失的任务，应使用 Celery、RQ、Dramatiq 等任务队列，或使用具备持久化工作流能力的系统。

### 28. 如何设计可靠重试？

**回答：** 只重试临时错误，并采用指数退避加随机抖动，设置最大次数和总截止时间。写操作必须先保证幂等。参数错误、权限错误等永久错误不应重试。超过次数后进入失败队列或人工处理，同时保留错误上下文。

### 29. Uvicorn 多 Worker 有什么作用？

**回答：** 单个 Worker 有一个事件循环，多 Worker 是多个进程，可以利用多核并隔离故障。进程之间不共享内存，因此会话、限流计数和任务状态不能只放在全局变量中，应放入 Redis 或数据库。Worker 数量要结合 CPU、内存、请求类型和压测决定。

### 30. Python 的迭代器和生成器有什么区别？

**回答：** 迭代器实现 `__iter__` 和 `__next__`，每次返回一个元素并在结束时抛出 `StopIteration`；包含 `yield` 的生成器函数会自动创建迭代器，并在每次产出值时保存执行现场。生成器适合流式处理和大数据集，但只能向前消费，资源清理和异常传播需要注意。

### 31. 装饰器的本质是什么？

**回答：** 装饰器接收函数或类并返回替代对象，`@decorator` 是定义后重新绑定名称的语法糖。常用于日志、鉴权、缓存和重试。实现时用 `functools.wraps` 保留元数据；异步函数需要返回异步包装器，带参数装饰器则再多一层闭包。

### 32. 上下文管理器解决什么问题？

**回答：** 上下文管理器通过 `__enter__/__exit__`，异步版本通过 `__aenter__/__aexit__`，确保资源在成功或异常路径都能释放。文件、锁、数据库事务和连接都适合使用 `with`。`__exit__` 的返回值还决定是否抑制异常，因此不应无意吞掉错误。

### 33. Python 的可变默认参数为什么危险？

**回答：** 默认参数在函数定义时只求值一次，`def f(items=[])` 中的列表会被多次调用共享，造成状态泄漏。通常用 `None` 作为默认值，在函数内部创建新对象。类似地，闭包中的变量是按名称后期绑定，循环创建函数时可用默认参数或工厂函数固定当前值。

### 34. 浅拷贝、深拷贝和赋值有什么区别？

**回答：** 赋值只是让两个名称指向同一对象；浅拷贝创建新容器，但嵌套对象仍共享；深拷贝递归复制对象图。深拷贝成本高且不一定符合业务语义，数据库会话、锁、文件等资源对象也不适合盲目复制，优先构造明确的数据模型。

### 35. Python 如何回收内存？

**回答：** 常见 CPython 主要使用引用计数，使多数对象在引用归零时立即释放，并用循环垃圾收集器处理互相引用。对象释放不代表进程 RSS 一定立刻下降，因为内存分配器可能保留内存供后续复用。排查泄漏要看对象增长和引用链，不能只看系统监控的一条曲线。

### 36. 线程、多进程和 asyncio 如何选择？

**回答：** 阻塞型 I/O 且依赖同步库时可用线程；纯 Python CPU 密集任务可用多进程利用多核；大量支持异步的网络 I/O 适合 asyncio。它们可以组合，但要控制池大小、序列化成本、共享状态和取消语义。选型依据任务性质，而不是“异步一定最快”。

### 37. `asyncio.gather` 和 `TaskGroup` 有什么区别？

**回答：** `gather` 便于聚合多个 awaitable 的结果，但错误和剩余任务如何处理取决于参数和调用方式；`TaskGroup` 提供结构化并发，作用域退出前等待所有子任务，某个任务非取消异常失败时会取消其余任务并汇总异常。有关联生命周期的并发任务更适合 TaskGroup。

### 38. 异步任务如何正确取消？

**回答：** 调用 `cancel()` 会在协程下一次可响应处抛出 `CancelledError`。协程应在 `finally` 中释放连接、锁和临时文件，清理后通常继续抛出取消异常，避免破坏超时和 TaskGroup 语义。阻塞函数无法仅靠取消协程立即停止，需要给底层调用设置超时或使用可中止的执行机制。

### 39. Pydantic 校验和 TypeScript 类型有什么根本区别？

**回答：** Pydantic 在运行时解析并校验真实输入，可拒绝非法数据或按配置转换类型；TypeScript 类型主要在编译期使用，生成 JavaScript 后通常不存在。来自网络、环境变量和数据库的不可信数据，即使在 TS 项目中也需要 Zod、class-validator 或 JSON Schema 等运行时校验。

### 40. FastAPI 请求生命周期大致是什么？

**回答：** ASGI 服务器接收请求后进入中间件链，路由匹配并解析参数，执行依赖图，调用路由函数，再按响应模型序列化，最后经过中间件返回。带 `yield` 的依赖在响应后执行清理。理解顺序有助于正确放置事务、日志、异常处理和请求级上下文。

### 41. FastAPI 的 lifespan 适合做什么？

**回答：** lifespan 用于应用启动和关闭阶段管理共享资源，例如创建数据库连接池、HTTP 客户端、模型或缓存连接，并在关闭时释放。不要在每个请求重复创建昂贵客户端，也不要假设多 Worker 之间共享 lifespan 中的对象，每个进程都会独立初始化。

### 42. FastAPI 为什么常返回 422？

**回答：** 当请求能被解析为 HTTP，但路径、查询参数或请求体不符合声明的 Schema 时，FastAPI 会返回验证错误，常见状态为 422。生产接口可保留字段级错误供前端定位，同时转换为统一错误结构；不要把内部模型字段或敏感校验细节全部暴露。

### 43. 数据库会话为什么通常按请求管理？

**回答：** 请求开始时取得会话，请求结束时提交或回滚并归还连接，使事务边界清晰且避免连接泄漏。不能把同一个 ORM Session 在并发请求或任务间共享。长任务应建立自己的会话和事务，避免把 Web 请求事务跨越外部模型调用。

## 三、鉴权、安全与多用户隔离

### 44. Authentication 和 Authorization 有什么区别？

**回答：** Authentication 回答“你是谁”，例如登录并验证 token；Authorization 回答“你能做什么”，例如普通用户不能访问管理员接口。认证成功不代表可以访问任意资源。

### 45. JWT 的结构和校验过程是什么？

**回答：** JWT 通常由 Header、Payload、Signature 三部分组成。Payload 只是 Base64URL 编码，并未加密，不能放密码等敏感信息。服务端需验证签名、算法、过期时间、签发者、受众等声明，然后再做权限和资源归属检查。

### 46. Access Token 和 Refresh Token 怎样设计？

**回答：** Access Token 生命周期短，用于访问接口；Refresh Token 生命周期长，只用于换取新 token。刷新时应支持轮换：每次使用后作废旧 Refresh Token，并记录 token family；发现旧 token 被再次使用时，撤销整组会话。

Web 场景可把 Refresh Token 放在 `HttpOnly + Secure + SameSite` Cookie 中，降低被脚本读取的风险。Access Token 放内存还是 Cookie，要结合 CSRF 防护和部署方式选择。

### 47. JWT 如何注销？

**回答：** 纯无状态 JWT 在过期前无法天然撤回。常用方案是短期 Access Token + 服务端保存 Refresh Token 会话；注销时撤销刷新会话，Access Token 等待短时间自然过期。高风险系统还可维护 `jti` 黑名单或用户 token version，但会引入状态查询。

### 48. RBAC 和 ABAC 有什么区别？

**回答：** RBAC 根据角色授予权限，简单易管；ABAC 根据用户、资源、动作和环境属性动态判断，更灵活但规则更复杂。项目初期可以用 RBAC 控制功能权限，再用资源归属条件保证用户只能访问自己的账单。

### 49. 如何实现用户数据隔离？

**回答：** 每张用户数据表保存 `user_id`，查询和更新都必须由后端从认证上下文注入 `user_id`，不能相信客户端传入的值。更新或删除使用 `WHERE id = ? AND user_id = ?`，返回 404 可避免泄露资源是否存在。还要为常用查询建立包含 `user_id` 的联合索引。

### 50. XSS、CSRF 和 SQL 注入分别如何防护？

**回答：**

- XSS：默认转义不可信内容，限制危险 HTML，使用 CSP，敏感 Cookie 设置 HttpOnly。
- CSRF：SameSite Cookie、CSRF Token，并校验 Origin/Referer；Bearer Token 若不由浏览器自动附带，风险模型不同。
- SQL 注入：使用参数化查询或 ORM 参数绑定，不能拼接用户输入；数据库账号遵守最小权限。

### 51. 密码应如何存储？

**回答：** 使用 Argon2id、bcrypt 等专用密码哈希算法，每个密码使用随机盐，并配置合适成本；不能明文存储，也不能只做普通 SHA 哈希。登录接口还需要限速、失败审计和防止账号枚举。

### 52. OAuth 2.0、OIDC 和 JWT 是什么关系？

**回答：** OAuth 2.0 是授权框架，OIDC 在其上增加身份认证；JWT 只是一种 Token 格式，OAuth 的 Access Token 不一定是 JWT。浏览器或移动端这类公开客户端常用授权码加 PKCE，服务端负责校验签发者、受众、签名和随机参数，不能把 ID Token 当作任意 API 的访问凭证。

### 53. Token 放 Cookie 还是 localStorage？

**回答：** localStorage 中的 Token 可被同源脚本读取，XSS 后容易泄露；HttpOnly Cookie 可阻止 JavaScript 读取，但会被浏览器自动携带，需要 SameSite、CSRF Token 和 Origin 校验。不存在对所有架构都最安全的单一答案，应结合跨域部署、刷新方式和威胁模型选择。

### 54. CORS 配置有哪些常见错误？

**回答：** 允许凭证时不能把允许来源设为 `*`；应精确配置来源、方法和请求头，并正确响应预检。动态回显 Origin 前必须校验白名单。CORS 只约束浏览器读取跨源响应，不是认证、权限控制或服务端防火墙。

### 55. 常见安全响应头有什么作用？

**回答：** CSP 限制可加载和执行的资源；HSTS 要求后续使用 HTTPS；`X-Content-Type-Options: nosniff` 减少 MIME 猜测；`frame-ancestors` 或旧式 `X-Frame-Options` 限制页面被嵌入，降低点击劫持。安全头应按实际资源加载方式测试，避免一刀切破坏功能。

### 56. 密钥如何管理和轮换？

**回答：** 密钥不进入代码、镜像、前端包和日志，由密钥管理系统或部署环境按最小权限注入。轮换时同时支持新旧密钥一段窗口，先用新密钥签发，再逐步停止验证旧密钥；每次访问应有审计，泄露后要能快速撤销并评估影响范围。

## 四、MySQL 与事务

### 57. 为什么数据库索引常用 B+ 树？

**回答：** B+ 树分支多、高度低，适合磁盘页；非叶子节点只存键和指针，单页能容纳更多索引项；叶子节点有序相连，范围查询高效。哈希索引适合等值查找，但不擅长范围和排序。

### 58. 聚簇索引和二级索引是什么？

**回答：** InnoDB 主键索引的叶子节点存整行数据，因此是聚簇索引；二级索引叶子节点通常保存索引列和主键。通过二级索引查未覆盖字段时，还需要按主键回到聚簇索引取数据，称为回表。

### 59. 联合索引的最左前缀原则是什么？

**回答：** 联合索引按列顺序排序，例如 `(user_id, created_at, id)` 可高效支持从 `user_id` 开始的条件以及之后的范围和排序。跳过最左列通常不能充分利用该索引。是否使用索引最终要看优化器和执行计划，不能只背规则。

### 60. 什么是覆盖索引？

**回答：** 查询需要的字段都可以从某个索引中获取，无需回表。它能减少随机 I/O，但索引列越多，存储和写入成本越高，不应为每条查询堆一个超宽索引。

### 61. ACID 分别是什么？

**回答：** 原子性保证事务内操作全成或全败；一致性表示事务使数据从一个合法状态到另一个合法状态；隔离性控制并发事务相互可见程度；持久性保证提交结果在故障后仍能恢复。数据库通过日志、锁和 MVCC 等机制共同实现这些性质。

### 62. 四种事务隔离级别是什么？

**回答：** 从弱到强通常是读未提交、读已提交、可重复读、串行化。它们依次解决脏读，并逐步限制不可重复读和幻读。隔离越强，并发能力通常越低。

MySQL InnoDB 默认常见配置是可重复读，并通过 MVCC 和必要的间隙/临键锁处理一致性读取与当前读问题。具体行为需要区分快照读和加锁读。

### 63. MVCC 如何工作？

**回答：** MVCC 为记录维护版本信息，通过 undo log 找到旧版本，事务根据 Read View 判断哪个版本可见。普通 `SELECT` 常使用一致性快照，读写之间减少互相阻塞；`SELECT ... FOR UPDATE` 等当前读会读取最新版本并加锁。

### 64. 什么情况下会发生死锁？如何处理？

**回答：** 多个事务以不同顺序持有并等待对方需要的锁，可能形成循环等待。应统一加锁顺序、缩短事务、建立合适索引以减少锁范围，并捕获死锁错误后对幂等事务做有限重试。不能靠把超时时间调大解决。

### 65. 什么是 N+1 查询？

**回答：** 先查一批主记录，再为每条记录各查一次关联数据，总查询数从 1 变成 N+1。可使用 JOIN、预加载或批量 `WHERE IN` 解决。优化前应关注结果集大小，避免一个 JOIN 产生巨量笛卡尔结果。

### 66. 一条慢 SQL 如何排查？

**回答：** 先用慢查询日志和 trace 确定 SQL 与实际耗时，再看 `EXPLAIN`/`EXPLAIN ANALYZE` 的扫描行数、索引、连接顺序、排序和临时表。之后判断是索引问题、SQL 写法、数据分布、锁等待还是连接池问题，并用真实数据验证优化效果。

## 五、Redis 与缓存

### 67. Redis 为什么快？

**回答：** 数据主要在内存中，数据结构针对常见操作优化；命令执行模型避免了大量共享数据加锁；I/O 多路复用可以处理大量连接。Redis 仍可能被大 Key、慢命令、网络、持久化和内存淘汰影响，不能简单理解为“所有操作都恒定很快”。

### 68. 常见 Redis 数据结构和场景有哪些？

- String：缓存对象、计数器、分布式锁的值。
- Hash：对象字段。
- List：简单队列，但可靠消息更适合 Stream 或专业消息系统。
- Set：去重、标签、共同关注。
- Sorted Set：排行榜、按时间或分值排序。
- Stream：消费组和可确认消息流。

### 69. Cache Aside 是什么？

**回答：** 读请求先查缓存，未命中则查数据库并回填；写请求先更新数据库，再删除缓存。删除而不是直接更新缓存可以减少并发覆盖和无效维护，但仍存在短暂不一致，需要结合过期时间、重试删除或消息通知达到业务需要的一致性。

### 70. 缓存穿透、击穿和雪崩有什么区别？

**回答：**

- 穿透：大量查询不存在的数据，缓存一直未命中。可做参数校验、缓存空值、布隆过滤器和限流。
- 击穿：一个热点 Key 失效，大量请求同时回源。可使用互斥重建、逻辑过期或提前刷新。
- 雪崩：大量 Key 同时失效或缓存整体不可用。可让过期时间加随机值、多级缓存、限流降级，并提高 Redis 可用性。

### 71. Redis 分布式锁需要注意什么？

**回答：** 获取锁使用带过期时间的原子 `SET key value NX PX`；value 使用唯一请求标识；释放时用 Lua 脚本先比对 value 再删除，防止误删别人的锁。还要考虑任务超过租期、GC 暂停、主从切换和网络分区。对强一致写入，数据库唯一约束、版本号或专门协调系统通常更可靠。

### 72. 如何用 Redis 保存会话和任务状态？

**回答：** 用不可猜测的 session/task ID 做键，值包含用户 ID、状态、版本和必要上下文，设置 TTL，并在每次读取时校验归属。长任务状态不能只依赖 Pub/Sub，因为订阅者离线时消息会丢失；需要恢复时使用 Stream、数据库或持久化任务队列。

### 73. Redis 的 RDB 和 AOF 有什么区别？

**回答：** RDB 周期性生成数据快照，文件紧凑、恢复快，但故障时可能丢失最近一次快照后的数据；AOF 记录写命令并按配置刷盘，可缩小数据丢失窗口，但文件和重写成本更高。两者可以同时使用。持久化、复制和高可用解决的问题不同，不能只开主从就认为数据不会丢。

### 74. Redis 过期和淘汰有什么区别？

**回答：** 过期是键达到 TTL 后不再有效，Redis 通过访问时检查和周期抽样删除；淘汰是在达到内存上限后，按 `noeviction`、LRU/LFU、随机等策略主动移除键。缓存与会话数据的淘汰容忍度不同，应分实例或明确策略，避免关键状态被当缓存淘汰。

### 75. Redis Sentinel 和 Cluster 分别解决什么？

**回答：** Sentinel 监控主从并在主节点故障时选举和切换，重点是高可用，不自动把数据分片；Cluster 使用哈希槽把键分布到多个主节点，同时提供故障转移，用于容量和吞吐扩展。多 Key 操作、事务和 Lua 在 Cluster 中通常要求相关键位于同一槽。

### 76. Redis Pub/Sub 和 Stream 有什么区别？

**回答：** Pub/Sub 是实时广播，订阅者离线时消息不会补发，也没有确认和消费进度；Stream 保存消息 ID，支持历史读取、消费组、待确认列表和重投。Stream 能提供更可靠的轻量消息能力，但跨系统事务、复杂路由和长期积压场景仍可能更适合专业消息队列。

### 77. Pipeline、事务和 Lua 脚本有什么区别？

**回答：** Pipeline 批量发送命令以减少网络往返，不保证命令组的隔离；`MULTI/EXEC` 保证事务中的命令连续执行，但不提供传统数据库式回滚；Lua 脚本在 Redis 中原子执行，适合读后判断再写。脚本应保持短小，避免长时间阻塞命令处理。

### 78. 如何发现和治理 Redis 大 Key？

**回答：** 通过采样、内存分析和慢日志找到占用大或元素过多的键，再按业务拆分、分页读取、限制集合大小和设置生命周期。直接同步删除大 Key 可能阻塞，宜使用渐进或异步删除能力。治理前要区分“内存大”和“单次操作慢”两个问题。

### 79. Redis 热 Key 会造成什么问题？

**回答：** 大量流量集中到一个 Key 或分片，会让集群总容量充足但单节点 CPU 或网络先饱和。可使用进程内短 TTL 缓存、请求合并、只读副本、Key 拆分和热点预热。写热点不能随意复制，否则会引入一致性问题。

### 80. 缓存更新为什么常见“先写数据库，再删缓存”？

**回答：** 先写数据库确保权威数据提交成功，再删缓存让后续读取回源重建。若先删缓存再写库，并发读可能把旧值重新写回缓存。即便采用推荐顺序，删除失败和并发时序仍会产生短暂不一致，需要 TTL、重试、消息或订阅变更日志兜底。

## 六、SSE、WebSocket 与流式响应

### 81. SSE 和 WebSocket 如何选择？

| 维度 | SSE | WebSocket |
| --- | --- | --- |
| 通信方向 | 服务端到客户端单向 | 全双工 |
| 协议 | HTTP 长连接 | HTTP Upgrade 后使用 WebSocket 帧 |
| 浏览器能力 | `EventSource` 自动重连 | 需自行处理重连与协议 |
| 数据格式 | 文本事件 | 文本和二进制 |
| 适用场景 | 模型输出、通知、进度 | 聊天、协作、游戏、双向实时控制 |

AI 对话通常先选 SSE，因为主要流量方向是服务端向浏览器推 token，基础设施也更容易兼容。

### 82. SSE 生产环境要处理什么？

**回答：** 设置正确的 `Content-Type: text/event-stream`，定期发送心跳，禁用代理缓冲，处理断线和客户端取消，必要时使用事件 ID 恢复。服务端还要设置并发上限和超时，避免连接无限占用资源。

### 83. 什么是背压？

**回答：** 生产者生成速度超过消费者处理速度时，数据会不断堆积。可使用有界队列、暂停读取、批量发送、丢弃可丢事件或降低生成速率。若完全没有上限，慢客户端可能持续占用内存并拖垮服务。

### 84. 用户点击“停止生成”后，后端应做什么？

**回答：** 前端取消请求只是第一步。服务端要感知连接断开，取消当前协程，并尽可能取消上游模型请求；对已经调用的外部工具要定义可取消与不可取消边界。最后保存已生成内容和取消状态，避免任务一直显示“进行中”。

## 七、Node.js 与 NestJS

### 85. Node.js 为什么适合 BFF？

**回答：** Node.js 擅长 I/O 密集服务，TypeScript 类型可与前端共享，生态适合接口聚合、SSR、CLI 和工程工具。BFF 的主要工作通常是并发请求下游、转换数据和鉴权，而不是重 CPU 计算，因此与 Node.js 的事件循环模型匹配。

### 86. Node.js 事件循环的基本原理是什么？

**回答：** JavaScript 主线程执行回调；网络和部分系统操作交给操作系统或线程池；结果就绪后进入相应队列，再由事件循环调度。Promise 回调属于微任务，会在当前调用栈结束后、进入后续事件循环阶段前执行。大量同步计算仍会阻塞所有请求。

### 87. `process.nextTick`、Promise 和 `setTimeout` 的顺序是什么？

**回答：** 在 Node.js 中，当前调用栈结束后通常先清空 `process.nextTick` 队列，再处理 Promise 等微任务，然后进入定时器等事件循环阶段。具体输出还受运行上下文和 Node 版本影响。更重要的是避免递归堆积 `nextTick` 或微任务导致 I/O 饥饿。

### 88. NestJS 的 Module、Controller、Provider 是什么？

**回答：** Module 组织能力边界和依赖；Controller 接收请求并调用用例；Provider 通常承载服务、仓储或客户端，通过依赖注入获得。良好结构应让 Controller 保持薄，业务逻辑可独立测试。

### 89. NestJS 中 Middleware、Guard、Pipe、Interceptor、Filter 如何区分？

- Middleware：路由处理前的通用请求逻辑。
- Guard：决定请求是否允许进入，常用于认证授权。
- Pipe：参数转换和校验。
- Interceptor：调用前后增强，如响应包装、缓存、耗时和超时。
- Exception Filter：捕获异常并转换响应。

### 90. NestJS 的依赖注入有什么价值？

**回答：** 类声明自己需要的抽象，由容器负责创建和连接实例，从而降低模块耦合，并便于测试时替换数据库或外部 API。依赖注入不是自动消除耦合；如果 Service 直接依赖大量具体实现，结构仍然会变差。

### 91. BFF 聚合多个下游接口时如何提高可靠性？

**回答：** 独立请求并发执行；为每个下游设置超时和错误分类；关键数据失败则整体失败，非关键数据可降级；对临时错误做有限重试；使用熔断和限流保护系统；传递 trace ID。不能无条件 `Promise.all`，因为任一失败会直接拒绝，可根据业务使用 `Promise.allSettled` 并显式处理部分结果。

### 92. 什么时候用 Worker Threads 或子进程？

**回答：** 图片处理、压缩、复杂解析等 CPU 密集任务会阻塞事件循环，可交给 Worker Threads；需要更强隔离或运行其他程序时可使用子进程。普通数据库和 HTTP 请求不需要为了“并发”创建 Worker。

### 93. Node.js 事件循环有哪些主要阶段？

**回答：** libuv 事件循环会依次处理 timers、pending callbacks、poll、check、close callbacks 等阶段；`setImmediate` 主要在 check 阶段，定时器在 timers 阶段。阶段之间还会处理微任务。面试重点不是死背所有内部队列，而是说明长时间同步计算会阻塞后续回调。

### 94. Promise 微任务、`queueMicrotask` 和 `process.nextTick` 有什么关系？

**回答：** 当前 JavaScript 调用栈结束后，Node 会在继续事件循环前处理微任务；`process.nextTick` 使用 Node 特有队列，优先级很高，递归安排可能饿死 I/O。现代代码优先使用标准 Promise 或 `queueMicrotask` 语义，只在确实需要兼容的 Node API 边界使用 nextTick。

### 95. Node.js Stream 和背压怎样工作？

**回答：** Stream 分块处理数据，避免一次把整个文件或响应装入内存。Writable 的 `write()` 返回 `false` 表示内部缓冲达到阈值，生产者应等待 `drain`；使用 `pipe`/`pipeline` 可自动传递背压和错误。忽略背压会造成内存增长和 GC 抖动。

### 96. CommonJS 和 ES Module 有什么区别？

**回答：** CommonJS 使用 `require/module.exports`，加载语义偏同步；ESM 使用静态 `import/export`，便于静态分析并支持顶层 await。Node 会根据扩展名和 `package.json` 的 `type` 判断模块体系。混用时要关注默认导出互操作、路径解析、缓存和测试工具配置。

### 97. Worker Threads、Cluster 和进程管理器如何区分？

**回答：** Worker Threads 在同一进程中创建独立 JS 执行线程，可传输或共享部分内存，适合 CPU 计算；Cluster 或多进程通过多个进程共享监听端口，利用多核处理请求，内存隔离更强；进程管理器负责拉起、重启和日志等运维能力。它们解决的层次不同。

### 98. Node.js 服务常见内存泄漏来源有哪些？

**回答：** 无界 Map 或缓存、未移除的 EventEmitter 监听器、定时器、闭包、未结束的请求与 Stream 都会保留对象。排查时观察堆是否在 GC 后仍持续增长，比较 heap snapshot 的对象数量和保留路径，并监控事件循环延迟、外部内存和 RSS。

### 99. AsyncLocalStorage 有什么用途？

**回答：** 它在异步调用链中保存请求级上下文，例如 trace ID、租户和日志字段，避免层层传参。上下文丢失通常来自不正确的异步资源封装或越过生命周期；不能在其中存巨大对象，也不能把它当权限校验的唯一来源。

### 100. NestJS Provider 的作用域有哪些？

**回答：** 默认单例作用域在应用生命周期复用实例；request 作用域为每个请求创建实例；transient 每次注入创建。请求作用域会沿依赖链传播并增加创建成本，因此只有确实依赖请求上下文时使用，普通无状态 Service 保持单例。

### 101. NestJS 如何处理循环依赖？

**回答：** `forwardRef` 可以暂时解除模块或 Provider 的构造顺序问题，但循环依赖往往说明边界不清。更好的做法是抽取共同能力、通过事件或接口解耦，或者重新划分模块。不要把 `forwardRef` 当作常规架构手段。

### 102. NestJS 的生命周期钩子有什么用途？

**回答：** 初始化钩子适合在依赖创建后执行连接或加载，启动钩子适合确认应用就绪；关闭钩子用于停止消费、关闭连接和优雅退出。要显式启用并处理进程终止信号，且不要在构造函数里执行需要异步等待的重资源初始化。

## 八、前后端协作与 React 数据层

### 103. 服务端状态和客户端状态有什么区别？

**回答：** 服务端状态来自远端，具有缓存、过期、并发更新和重试等问题，适合 TanStack Query 等工具；客户端状态是当前页面交互状态，如弹窗和筛选条件，适合组件状态或轻量状态库。把接口数据全部复制到全局 Store，会产生双份真相和同步问题。

### 104. 乐观更新如何实现？

**回答：** 发请求前保存旧缓存并立即更新 UI；失败时回滚；成功后用服务端结果校准或重新获取。涉及余额、库存等强约束数据时要谨慎，服务端仍是最终权威，并用版本号或幂等键处理并发。

### 105. SSR、CSR 和 Hydration 是什么？

**回答：** CSR 在浏览器生成主要页面；SSR 在服务端先生成 HTML，首屏和 SEO 较好；Hydration 是客户端 React 接管服务端 HTML 并绑定交互。服务端和客户端首次渲染结果不同会产生 hydration mismatch，常见原因包括随机值、时间、浏览器专属 API 和不一致数据。

### 106. CORS 是什么？

**回答：** CORS 是浏览器执行的跨源访问控制机制，服务端通过响应头声明允许哪些源、方法和请求头。某些非简单请求会先发送 OPTIONS 预检。CORS 不是服务端接口的身份认证，非浏览器客户端不受浏览器同源策略保护。

### 107. React 的 render 和 commit 阶段有什么区别？

**回答：** render 阶段调用组件并计算下一棵 UI 树，必须保持纯函数语义，React 可以暂停、重试或丢弃这次计算；commit 阶段把差异真正应用到 DOM，并运行相应的布局 Effect。组件函数被调用不代表 DOM 一定改变，性能分析要区分两阶段。

### 108. Virtual DOM 和 reconciliation 是什么？

**回答：** React 用 JavaScript 对象描述 UI，并在状态变化后比较前后元素树，决定最少需要提交哪些宿主环境变更。协调算法依赖元素类型和 `key` 等信息做启发式匹配，不是对任意树求理论最小编辑距离。Virtual DOM 的价值还包括声明式编程和跨平台抽象，不能简单说一定比手写 DOM 快。

### 109. `key` 为什么不能随便使用数组下标？

**回答：** `key` 帮助 React 在同级列表中识别元素身份。列表插入、删除或排序时，数组下标会对应到不同数据，可能造成组件状态错位和不必要的重建。应使用同一数据在生命周期内稳定且唯一的业务 ID；`key` 只需在同级兄弟中唯一。

### 110. React 状态为什么像一次渲染的快照？

**回答：** 每次 render 都看到当次固定的 state 和 props，事件处理函数闭包也捕获这一快照。调用 setter 是安排下一次渲染，不会立刻修改当前变量。连续依赖前值的更新应使用函数式写法，例如 `setCount(c => c + 1)`，让 React 按队列应用。

### 111. React 的批处理是什么？

**回答：** React 会把同一批事件中的多个状态更新合并，在处理结束后统一渲染，以减少重复工作。批处理不代表多次更新自动变成一次赋值；直接使用快照值可能互相覆盖，函数式更新才适合基于前值连续计算。只有与外部系统同步的极少场景才考虑强制同步提交。

### 112. `useEffect` 应该用来做什么？

**回答：** Effect 用于让 React 与组件外部系统同步，例如订阅、网络连接、浏览器 API 或第三方组件。能在 render 中计算出的派生值不需要 Effect，用户动作应尽量放在事件处理器。依赖变化前会先运行上次清理，卸载时也会清理。

### 113. Effect 中的竞态和陈旧闭包如何处理？

**回答：** 异步请求可能乱序返回，旧请求覆盖新状态；可用 AbortController 取消、在清理函数中标记失效，或使用成熟的数据请求库。陈旧闭包来自回调捕获旧 render 的值，应正确声明依赖、使用函数式更新或 ref，而不是随意关闭 lint 规则。

### 114. `useMemo`、`useCallback` 和 `React.memo` 有什么区别？

**回答：** `useMemo` 缓存计算结果，`useCallback` 缓存函数引用，`React.memo` 在 props 浅比较相同的情况下跳过子组件重新渲染。它们都是性能优化，不保证语义，也有比较、依赖和内存成本。先用 Profiler 找到真实热点，再保证传入值稳定，避免无差别包裹。

### 115. `useRef` 和 state 有什么区别？

**回答：** ref 在多次渲染间保存同一个可变容器，修改 `current` 不触发渲染，适合 DOM 节点、定时器 ID 和不参与展示的实例数据；state 的更新会安排重新渲染。渲染需要使用的数据不应藏在 ref 中，否则 UI 不会自动同步。

### 116. 受控组件和非受控组件有什么区别？

**回答：** 受控表单由 React state 作为值的来源，便于即时校验、联动和统一提交；非受控表单由 DOM 保存当前值，通过 ref 或 FormData 读取，代码更少且可减少高频渲染。复杂表单库常在两者之间做优化，选择取决于交互需求。

### 117. Error Boundary 能捕获哪些错误？

**回答：** Error Boundary 捕获其子树在渲染、生命周期和构造过程中的错误，并显示降级 UI；它通常不能捕获事件处理器、任意异步回调、服务端渲染或自身内部的错误。网络错误仍需请求层显式处理，路由和模块级边界可缩小故障影响。

### 118. Suspense 解决什么问题？

**回答：** Suspense 让子树在代码或框架支持的数据尚未就绪时显示 fallback，并与并发渲染配合协调展示顺序。它不是自动的数据请求库，数据源必须与 Suspense 集成。边界过大导致整页闪烁，过小则增加复杂度，应围绕用户可感知的加载单元划分。

### 119. Hydration mismatch 为什么出现？

**回答：** 服务端生成的首屏 HTML 与客户端第一次 render 结果不同会造成 mismatch。常见原因有随机数、当前时间、浏览器专属分支、无效 HTML 嵌套和两端数据不一致。应让首 render 可复现，把客户端特有逻辑放到 Effect 或明确的客户端边界。

### 120. React Server Components 和 SSR 是一回事吗？

**回答：** SSR 是把组件输出先生成 HTML；Server Components 是只在服务端执行、结果以专用协议传给客户端的组件模型，可直接访问服务端数据并减少客户端 JS。二者可以组合。Server Component 不能使用浏览器 API和客户端交互 Hook，跨边界的 props 也必须可序列化。

### 121. `startTransition` 和 `useDeferredValue` 有什么用途？

**回答：** 它们把某些更新标记为非紧急，让输入等紧急交互保持响应。`startTransition` 包裹可以延后的状态更新，`useDeferredValue` 让某个值的消费落后于最新值。它们不会让昂贵计算消失，仍需结合拆分、缓存、虚拟列表或服务端优化。

### 122. TypeScript 中 `any`、`unknown` 和 `never` 有什么区别？

**回答：** `any` 基本关闭类型检查并会传播；`unknown` 表示未知值，使用前必须缩小类型；`never` 表示不可能出现的值或永不返回的路径，可用于联合类型穷尽检查。外部输入优先接成 unknown，再通过运行时校验转换为可信类型。

### 123. `type` 和 `interface` 如何选择？

**回答：** 两者都能描述对象结构。interface 支持声明合并和继承，适合可扩展公共对象契约；type 可表达联合、交叉、条件和映射类型，组合能力更广。项目应保持一致习惯，不必把选择夸大为性能或运行时区别，因为二者都会被擦除。

### 124. TypeScript 的结构化类型是什么？

**回答：** 类型兼容主要看对象是否具有所需结构，而不是是否显式声明继承，因此来自不同位置但字段兼容的对象可以赋值。这便于组合，也意味着领域 ID 都是 string 时容易互相混用；可用品牌类型或封装对象增强名义区分。

### 125. 泛型和条件类型解决什么问题？

**回答：** 泛型在保持类型关系的同时复用实现，例如输入元素类型决定返回类型；条件类型根据类型关系选择结果，映射类型可批量变换属性。复杂类型应服务于真实 API，过度追求类型体操会增加编译时间、报错难度和维护成本。

## 九、测试、可观测性与部署

### 126. 应该怎样设计测试层次？

**回答：** 业务规则使用快速单元测试；数据库仓储和外部边界使用集成测试；登录、创建账单、发起分析等关键路径使用少量端到端测试。不要用大量 E2E 覆盖所有分支，也不要只 mock 到无法发现真实接口问题。

### 127. FastAPI 项目重点测试什么？

**回答：** 权限和用户隔离、事务回滚、参数边界、幂等、缓存失效、外部模型超时、流式中断和任务重试。通过依赖覆盖替换数据库或当前用户，但关键集成测试应连接真实数据库和 Redis 容器。

### 128. 什么是日志、指标和 Trace？

**回答：** 日志记录离散事件和上下文；指标描述一段时间内的聚合趋势，如 QPS、错误率和延迟分位数；Trace 展示一次请求跨服务和外部调用的完整链路。三者通过 request/trace ID 关联，才能从告警快速定位具体请求。

### 129. 为什么看 P95/P99，而不只看平均延迟？

**回答：** 平均值会掩盖长尾。P95 表示 95% 的请求不超过该值，P99 更能反映少数用户遇到的慢请求。AI 服务还应拆分首 token 延迟、总生成时间、模型耗时、工具耗时和排队时间。

### 130. Docker 镜像如何优化？

**回答：** 使用小而明确的基础镜像、多阶段构建、锁定依赖、合理利用构建缓存，以非 root 用户运行，不把密钥打进镜像，并设置健康检查。容器应把状态放在外部存储，日志输出到标准输出供平台采集。

### 131. 服务如何优雅关闭？

**回答：** 收到终止信号后先停止接收新请求，再等待在途请求到设定期限，关闭数据库和 Redis 连接，保存或交接任务状态后退出。长连接和后台任务尤其需要明确关闭策略，否则发布时会丢消息或留下半完成任务。

### 132. 如何做一次有意义的压测？

**回答：** 先定义目标场景、并发模型和 SLO，再使用接近真实的数据与请求比例，逐级增加负载。记录吞吐、P50/P95/P99、错误率、CPU、内存、连接池和数据库慢查询。压测环境和依赖容量要说明，不能只报一个脱离条件的 QPS。

### 133. 单元测试、集成测试、契约测试和 E2E 各自负责什么？

**回答：** 单元测试快速验证纯业务规则；集成测试连接真实数据库、缓存或框架边界；契约测试验证服务提供方和调用方对接口结构的理解一致；E2E 从用户入口验证少量关键链路。测试金字塔不是固定比例，目标是用最低成本覆盖最有价值的风险。

### 134. Mock 过多为什么会让测试失真？

**回答：** 如果把 ORM、HTTP 序列化和所有下游都按实现细节 mock，测试只证明 mock 与代码相互配合，真实 Schema、事务和网络行为仍可能失败。纯业务依赖可以替换，关键基础设施更适合用容器或轻量真实实例；第三方接口可用录制或契约测试验证边界。

### 135. CI 流水线应该包含什么？

**回答：** 提交阶段执行格式、静态检查、类型检查、单元与关键集成测试，并构建可部署产物；合并后做镜像扫描、迁移检查和环境部署，再运行冒烟测试。流水线应快速反馈且结果可复现，失败不得通过重复点击掩盖偶发问题。

### 136. 蓝绿发布和金丝雀发布有什么区别？

**回答：** 蓝绿维护两套完整环境，验证新版本后整体切流，回滚快但资源成本高；金丝雀先让少量实例或用户使用新版本，观察指标后逐步扩大，能降低未知风险但路由和数据兼容更复杂。两者都要求数据库变更可向后兼容。

### 137. 数据库迁移为什么采用 Expand-Migrate-Contract？

**回答：** 先新增兼容字段或表，让新旧代码都能运行；再回填数据、双写或切换读取；确认旧版本和旧数据退出后才删除旧结构。这样避免应用发布和 DDL 必须在同一瞬间完成，滚动发布失败时也保留回退路径。

### 138. SLI、SLO 和 SLA 是什么？

**回答：** SLI 是实际测量指标，如成功率和延迟；SLO 是团队希望达到的目标；SLA 是对外承诺及可能的违约责任。错误预算由目标允许的失败量推导，可用来平衡稳定性投入与发布速度。指标必须从用户体验定义，而不是只看机器存活。

### 139. 如何设计告警避免告警疲劳？

**回答：** 优先对用户可感知的错误率、延迟和容量风险告警，设置持续窗口和分级，而不是每个瞬时尖峰都通知。告警要有负责人、上下文、仪表盘和处置手册；无法行动的告警应删除或降级。发布事件应与告警时间线关联。

### 140. OpenTelemetry 能解决什么问题？

**回答：** OpenTelemetry 提供生成和传递 Trace、Metric、Log 遥测数据的标准 API、SDK 与协议，降低对单一观测厂商的绑定。它不会自动给出业务答案，仍需设计 span 边界、属性基数、采样率和敏感数据脱敏，并确保上下文跨进程传播。

## 十、AI 应用工程

### 141. AI 应用为什么不能只做一次模型调用？

**回答：** 生产系统还需要身份与配额、输入校验、上下文管理、工具权限、结构化输出、超时重试、流式传输、成本统计、内容安全、评测和可观测性。模型只是系统中的一个不稳定外部依赖。

### 142. Agent Loop 的基本流程是什么？

**回答：** 将用户目标和工具描述交给模型；模型选择工具并生成结构化参数；程序校验参数、检查权限并执行工具；结果写回上下文；模型继续决策，直到给出最终答案或达到停止条件。必须设置最大步数、总超时、成本上限和重复调用检测。

### 143. Tool Calling 如何保证安全？

**回答：** 工具使用白名单和严格 Schema；服务端重新校验参数和权限；按用户注入数据范围；读写工具分级；高风险写操作增加确认和审计；工具结果作为不可信数据处理。模型只能选择预先注册的能力，不能直接执行任意代码或 SQL。

### 144. 如何防御 Prompt Injection？

**回答：** 不把外部内容当系统指令；明确区分指令与数据；敏感能力由代码权限控制而不是靠提示词；检索内容和工具输出做来源标记；最小化可用工具和凭证；对外部写操作增加策略校验。Prompt 本身不能构成安全边界。

### 145. AI 流式响应中如何保存消息？

**回答：** 先创建一条 `pending` 消息并获得 ID，流式增量可以只在内存或 Redis 中短暂累积，按时间或字符数批量持久化，完成后原子更新为 `completed`。失败或取消则保存已有内容和终止原因。这样可以恢复会话，也避免每个 token 都写数据库。

### 146. 如何评估 AI 功能？

**回答：** 建立包含正常、边界和对抗样本的固定数据集，定义任务成功率、工具选择正确率、参数正确率、事实性、延迟和成本等指标。自动评审适合规模化回归，但关键样本要人工抽检。每次修改 Prompt、模型或工具都跑相同评测集。

### 147. MCP 是什么？

**回答：** MCP 为模型应用连接工具、资源和提示提供统一协议，减少每个客户端与每个工具单独适配的成本。MCP Server 负责暴露能力，但认证、授权、输入校验和审计仍由实现者负责。用 TypeScript 编写 MCP Server 或 CLI，能很好体现 Node.js 工程能力。

### 148. RAG 的基本链路是什么？

**回答：** 离线阶段清洗文档、切块、生成向量并建立索引；在线阶段改写或理解查询，召回候选片段，必要时重排，再把证据与问题交给模型生成答案。完整系统还要保存来源、处理权限过滤、无答案场景、索引更新和评测，不能把“接了向量库”当作 RAG 完成。

### 149. 文档切块如何选择大小和重叠？

**回答：** 块太小会丢失上下文，太大则降低召回精度并浪费上下文窗口。应按标题、段落、代码结构等语义边界切分，再依据文档类型、模型和查询用评测选择长度与重叠。重叠能缓解边界信息丢失，但也会产生重复召回和存储成本。

### 150. 向量检索、关键词检索和混合检索如何选择？

**回答：** 向量检索擅长语义近似，但可能漏掉精确编号、专有名词和代码符号；BM25 等关键词检索对精确词匹配稳定。混合检索分别召回后融合，再用重排模型提高前几名质量。过滤条件应在召回阶段尽早应用，尤其是租户和权限边界。

### 151. Rerank 为什么有用？

**回答：** 第一阶段检索追求低成本召回较多候选，重排模型再同时理解查询与候选内容，给出更精确的相关性顺序。它能改善送给大模型的证据质量，但会增加延迟和成本。需要通过 Recall@K、MRR、答案正确率等指标判断是否值得。

### 152. 结构化输出为什么仍要校验？

**回答：** JSON Schema 或模型的结构化输出能力能提高格式稳定性，但字段值仍可能越界、与数据库状态冲突或包含越权参数。服务端必须做运行时 Schema、业务规则和权限校验；失败时可把明确的校验错误反馈给模型有限修复，不能无限循环。

### 153. AI 应用如何控制 Token 和成本？

**回答：** 记录每个租户、场景和模型的输入输出 Token、缓存命中与工具成本；压缩或摘要历史上下文，只注入相关资料；按任务难度路由模型，设置最大输出、总预算和并发配额。成本优化必须同时观察成功率，不能只通过截短上下文让质量下降。

### 154. 模型路由和降级如何设计？

**回答：** 按任务类型、风险、延迟和预算选择主模型，调用失败或超时后只对可安全重试的场景切换备用模型。降级可以返回非 AI 统计结果、较短答案或稍后处理，而不是静默给出质量不可控的内容。路由策略需要版本化并纳入评测。

### 155. 语义缓存有什么风险？

**回答：** 它用语义相似度复用已有回答，可降低延迟和成本，但相似问题可能因用户、时间、权限和上下文不同而不能共享。缓存键必须包含模型、Prompt 版本、租户和数据版本等边界；金融、权限或强时效问题应提高阈值或禁用。

### 156. Agent 的短期记忆和长期记忆如何区分？

**回答：** 短期记忆是当前任务的对话、工具结果和执行状态，受上下文窗口限制；长期记忆是跨会话保存的用户偏好、事实或摘要。写入长期记忆前应判断价值、来源和权限，支持用户查看与删除，并防止模型把推测永久保存成事实。

### 157. 工具调用为什么必须幂等？

**回答：** 模型、网络或编排器可能因超时重试同一调用，写工具若没有幂等键会重复创建订单、账单或通知。编排器应为逻辑步骤生成稳定调用 ID，工具端持久化请求摘要和结果；对无法幂等的外部副作用，要在执行前确认状态并设计补偿。

### 158. 如何避免 Agent 无限循环？

**回答：** 设置最大步数、总时限、Token 和费用上限；记录工具名与参数摘要，检测连续重复；给工具返回结构化错误并区分可重试与永久失败；必要时用状态机限制允许的转移。达到上限后返回可解释的部分结果和失败原因。

### 159. AI 可观测性应记录什么？

**回答：** 记录模型和 Prompt 版本、输入输出 Token、首 Token 与总延迟、工具链路、重试、缓存、成本、终止原因和评测反馈，并用 trace 串联一次请求。日志要对个人信息、密钥和模型输入做脱敏，生产 Prompt 也要有访问控制。

### 160. 离线评测和在线评测如何配合？

**回答：** 离线固定数据集适合版本回归和快速比较，包含正常、边界和对抗样本；在线通过灰度、用户反馈、任务完成率和人工抽检观察真实分布。LLM-as-a-judge 可扩大评测规模，但要校准偏差并保留关键样本的人工判断。

## 十一、项目场景题

### 161. 如何介绍“消费分析助手”？

可以按 60 秒版本回答：

> 这是一个面向个人消费记录的 AI 分析应用。前端使用 React/TypeScript，后端使用 FastAPI，MySQL 保存用户、账单和分析记录，Redis 保存会话状态、热点统计和短期任务状态。用户登录后只能访问自己的数据，可以导入或维护账单，再通过 Agent Loop 调用统计工具完成分类汇总、趋势分析和自然语言解释。模型输出通过 SSE 流式返回。系统对工具参数做 Pydantic 校验，并设置超时、最大步数、幂等键和失败重试；日志通过 trace ID 串联接口、数据库和模型调用。

### 162. 为什么这个项目选择 FastAPI？

> 项目的核心能力包括数据分析、Agent 编排和模型调用，Python 生态更直接；同时请求大量等待数据库和模型 I/O，FastAPI 的 ASGI 与异步接口适合这类负载。Pydantic 还能统一校验接口和工具参数。若有面向多个前端的接口聚合，我会在外层增加 NestJS BFF，而不是把 AI 逻辑复制到 Node.js。

### 163. 如何保证用户 A 看不到用户 B 的账单？

> 登录后从已验证 token 得到 user ID。仓储层所有账单查询都强制带 user ID，更新和删除也使用 `id + user_id` 条件，不接受客户端指定数据归属。数据库对 `(user_id, created_at, id)` 建联合索引。接口层还通过 RBAC 控制管理能力，并写集成测试验证横向越权。

### 164. 模型接口超时怎么办？

> 我把连接超时、首 token 超时、总超时分开设置。未产生副作用的临时网络错误可以指数退避重试；工具写操作只有具备幂等键时才重试。达到上限后把消息标记为失败，保留已生成内容和 trace ID，前端提供重试入口。并通过指标区分排队、模型和工具耗时。

### 165. 如何实现会话恢复？

> MySQL 保存消息和最终状态，Redis 保存进行中的短期上下文与任务进度。客户端重连时携带会话 ID 和最后事件 ID；服务端先校验用户归属，再补发缺失事件或从已持久化内容恢复。只用进程内内存无法支持多 Worker、发布重启和故障恢复。

### 166. Redis 挂了，系统还能运行吗？

> 先按数据重要性区分。缓存不可用时，普通查询可限流后回源数据库；会话短期状态丢失时从持久化消息重建；分布式锁或限流依赖 Redis 的功能需要降级或暂时拒绝，不能假装成功。通过短超时、熔断和告警避免大量请求堆积。

### 167. 如果让 NestJS 做 BFF，边界怎么划？

> NestJS 负责验证前端会话、聚合用户资料和分析结果、转换字段、提供面向页面的接口，也可以代理 SSE。FastAPI 继续拥有消费分析、Agent 和数据规则。BFF 不直接跨过服务修改核心数据，服务间身份和 trace 信息显式传递，避免形成第二套业务逻辑。

### 168. 这个项目最值得讲的难点是什么？

推荐选一个真实做过的点，用“问题—约束—方案—结果—复盘”回答：

> 问题是流式生成过程中用户刷新页面后，消息容易丢失或永久停在生成中。约束是不能每个 token 都写 MySQL，也要支持多 Worker。我的方案是先创建 pending 消息，用 Redis 保存短期增量并按批次落库，完成、失败和取消都更新终态；客户端用事件 ID 重连。这样减少了写放大，也支持刷新恢复。后续还可以通过压测确定批量大小，并增加清理超时任务的定时任务。

### 169. 如何量化项目成果？

不要编数字。可以在本地压测后记录：

- 并发数、持续时间、请求分布和机器配置。
- P50/P95/P99、错误率、吞吐和首 token 延迟。
- 加缓存前后的数据库查询量和延迟。
- 串行与并行工具调用的总耗时。
- 异常注入后重试成功率和恢复时间。

简历写法示例：

> 通过并行执行无依赖分析工具，将固定测试集的平均分析耗时由 X 秒降至 Y 秒；使用 Redis 缓存高频统计结果，使相同压测条件下 MySQL 查询量下降 Z%。

## 十二、高频追问速答

### 170. 接口为什么要超时？

防止请求无限占用线程、连接和内存；总超时还应小于上游调用者的超时，给错误处理留时间。

### 171. 为什么重试要加随机抖动？

避免大量客户端在同一时间再次请求，形成重试风暴。

### 172. 为什么不能把 session 放在进程内存？

多 Worker 不共享内存，重启会丢失，负载均衡后请求也不一定落到同一进程。

### 173. 为什么数据库连接池不能越大越好？

连接会消耗服务端内存和调度资源；过多并发还会增加锁竞争。连接池应结合数据库上限、实例数和实际等待时间设置。

### 174. 什么时候使用消息队列？

需要异步解耦、削峰、可靠重试或事件广播时使用。引入后要处理重复消费、顺序、积压和可观测性。

### 175. 如何处理重复消费？

消费者以业务唯一键做幂等，使用唯一约束或状态机保证重复消息不会重复产生业务结果。

### 176. 限流算法有哪些？

固定窗口简单但有边界突发；滑动窗口更平滑；漏桶以稳定速率处理；令牌桶允许一定突发。实际选择取决于是否允许突发和限流维度。

### 177. 什么是熔断？

下游连续失败达到阈值后暂时快速失败，避免继续堆积；一段时间后半开探测，成功则恢复，失败则继续断开。

### 178. 数据库迁移如何安全上线？

使用向后兼容的扩展—迁移—收缩过程：先加新字段或表，让新旧代码都能工作；迁移数据并切流；确认无旧版本后再删除旧结构。

### 179. 为什么配置和密钥要分开？

普通配置可以进入版本管理，密钥应由环境或密钥管理系统注入，支持轮换和最小权限，避免出现在代码、镜像和日志中。
