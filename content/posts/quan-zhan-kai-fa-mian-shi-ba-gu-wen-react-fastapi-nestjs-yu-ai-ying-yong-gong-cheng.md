这份手册服务于一条明确的技术主线：**React/TypeScript 负责前端，Python/FastAPI 负责 AI 应用后端，Node.js/NestJS 负责 BFF、CLI、MCP 与前端工程化。**

它不追求把所有后端语言都背一遍，而是帮助你回答三个问题：

1. 能不能独立完成一个前后端闭环？
2. 能不能把 AI Demo 做成可靠的在线服务？
3. 遇到并发、缓存、鉴权、失败和性能问题时，是否知道如何处理？

## 使用方法

每道题先记住“回答”里的主干，再理解“追问”。面试时建议按以下结构组织答案：

> 先给结论 → 解释原理 → 说明取舍 → 落到自己的项目。

例如回答“为什么使用 SSE”：

> 我的场景主要是服务端持续向浏览器推送模型输出，客户端很少在同一条连接上反向发送数据，因此 SSE 比 WebSocket 更简单，也能复用 HTTP 鉴权和网关。项目中我还处理了断线重连、心跳、取消生成和代理缓冲问题。如果要做实时协作或高频双向通信，我会改用 WebSocket。

## 一、全栈架构与接口设计

### 1. 什么是全栈开发？

**回答：** 全栈不是“每一层都会一点”，而是能围绕一个业务目标完成浏览器交互、接口设计、服务端逻辑、数据存储、部署和排障的闭环。真正重要的是理解各层边界：前端负责交互和展示，BFF 负责面向页面聚合，领域服务负责业务规则，数据库负责可靠存储，缓存和消息系统负责性能与解耦。

**项目表达：** 我的主线是 React/TypeScript + FastAPI。需要适配多个前端或聚合多个服务时，使用 NestJS 做 BFF；AI 推理、数据分析和 Agent 编排留在 Python 服务中。

### 2. 为什么不能把所有业务都写在前端或 BFF 中？

**回答：** 前端代码会下发到用户设备，不能保存密钥，也不能作为权限和金额等规则的可信边界。BFF 可以做协议转换、字段裁剪和接口聚合，但核心业务规则如果只存在于某一个 BFF，会导致多端逻辑不一致。鉴权最终校验、事务和领域规则应放在后端服务中。

### 3. 什么是 BFF？它解决什么问题？

**回答：** BFF 是 Backend for Frontend，为某一类前端提供定制接口。它可以聚合多个下游请求、裁剪字段、统一鉴权、转换协议，并减少前端与内部服务的耦合。

**代价：** 多了一层网络跳转和维护成本；如果把领域逻辑大量写进 BFF，会形成新的单体。BFF 应保持“面向体验的编排层”定位。

### 4. RESTful API 应该怎样设计？

**回答：** 用资源表达路径，用 HTTP 方法表达动作，例如 `GET /transactions`、`POST /transactions`、`PATCH /transactions/{id}`。状态码表达请求结果，请求体和响应体保持稳定结构，并统一分页、错误码、时间格式和字段命名。

常见状态码：

- `200` 查询或更新成功；`201` 创建成功；`204` 成功但无响应体。
- `400` 请求格式错误；`401` 未认证；`403` 已认证但无权限；`404` 资源不存在。
- `409` 状态冲突；`422` 语义或参数校验失败；`429` 请求过多。
- `500` 服务内部错误；`502/503/504` 通常与上游或服务可用性有关。

### 5. PUT 和 PATCH 有什么区别？

**回答：** PUT 通常表示用完整表示替换资源，PATCH 表示部分更新。PUT 在语义上应当幂等；PATCH 是否幂等取决于补丁定义，例如“将名称改为 A”是幂等的，“余额增加 10”不是。

### 6. 什么是幂等？如何实现？

**回答：** 同一个请求执行一次或多次，产生的最终业务结果相同。GET、PUT、DELETE 在 HTTP 语义上应当幂等，但具体实现仍需保证。

对创建订单、导入账单等操作，可以让客户端传 `Idempotency-Key`，服务端把键、用户、请求摘要和处理结果持久化。重复请求直接返回原结果。数据库唯一约束是最后防线，不能只依赖 Redis 锁。

### 7. 如何设计统一错误响应？

**回答：** 错误响应应包含稳定的业务错误码、可读信息、请求追踪 ID，以及必要的字段级错误；不要把堆栈和数据库细节暴露给客户端。

```json
{
  "code": "TRANSACTION_NOT_FOUND",
  "message": "账单不存在或无权访问",
  "requestId": "req_123",
  "details": []
}
```

HTTP 状态码给网关和通用客户端使用，业务错误码给产品逻辑和排障使用，两者不能互相替代。

### 8. 接口如何做分页？

**回答：** 数据量小、需要跳页时可用 `offset + limit`，实现简单，但深分页会扫描和丢弃大量记录，并且数据变动时可能重复或遗漏。信息流和大表更适合游标分页，以稳定排序字段加唯一 ID 作为游标，例如 `(created_at, id)`，查询下一页时使用范围条件。

### 9. 如何保证前后端类型一致？

**回答：** 以 OpenAPI 或 JSON Schema 作为接口契约，再生成 TypeScript 客户端和类型。Python 端用 Pydantic 校验，NestJS 端用 DTO 与运行时校验，前端不要把 TypeScript 类型误当成运行时校验。

版本变更优先做向后兼容：新增可选字段通常安全，删除字段、改类型或改语义需要版本管理和迁移窗口。

### 10. 一次请求在系统中经过哪些层？

**回答：** 常见链路是 CDN/负载均衡 → 网关或反向代理 → BFF/应用服务 → 缓存或数据库 → 外部模型服务。每层都可能增加超时和失败，因此要设置连接超时、读取超时、总截止时间和有限重试，并通过同一个 trace ID 串起日志。

## 二、Python 与 FastAPI

### 11. FastAPI 为什么性能较好？

**回答：** FastAPI 基于 ASGI，配合 Uvicorn 可以高效处理 I/O 并发；Starlette 提供 Web 能力，Pydantic 提供数据校验。性能主要来自异步 I/O 和较薄的框架层，而不是 Python 单线程突然变快。CPU 密集任务仍会阻塞事件循环，应交给进程池、任务队列或独立服务。

### 12. WSGI 和 ASGI 有什么区别？

**回答：** WSGI 面向同步请求响应模型；ASGI 支持异步调用、长连接和 WebSocket。传统 CRUD 用 WSGI 也可以，模型流式输出、并发访问外部 API 和 WebSocket 更适合 ASGI。

### 13. `async def` 一定比 `def` 快吗？

**回答：** 不一定。异步的优势是等待网络、数据库等 I/O 时把执行权交回事件循环，提高并发能力。CPU 计算不会因为 `async` 加速；在异步函数里调用阻塞库反而会卡住整个事件循环。

**追问：** FastAPI 可以在线程池中执行同步路由，但线程也有开销。应根据依赖库是否支持异步选择写法，不能机械地把函数全改成 `async`。

### 14. Python 事件循环如何工作？

**回答：** 协程运行到 `await` 且等待对象未完成时，会挂起并把控制权交给事件循环。事件循环监听 I/O 就绪事件，待结果可用后把协程放回可运行队列。它适合大量 I/O 并发，不等于多个 Python 字节码同时在多个 CPU 核心上执行。

### 15. GIL 是什么？

**回答：** 在常见 CPython 实现中，GIL 使同一进程内通常只有一个线程执行 Python 字节码。I/O 等待时会释放 GIL，所以线程仍适合 I/O 密集任务；纯 Python CPU 密集任务可使用多进程、原生扩展或独立计算服务。GIL 与数据库事务、协程安全是不同问题。

### 16. FastAPI 的依赖注入有什么用？

**回答：** `Depends` 可以声明并复用数据库会话、当前用户、权限检查和配置等依赖，还能处理请求结束后的资源清理。它让路由只关注用例，测试时也容易覆盖依赖。

### 17. Pydantic、SQLAlchemy 和 SQLModel 分别负责什么？

**回答：** Pydantic 负责输入输出的数据解析和校验；SQLAlchemy 是 ORM 与 SQL 工具；SQLModel 在两者之上提供更统一的模型写法。接口 DTO 和数据库实体最好仍保持边界，避免数据库字段无意中暴露到 API，也避免接口变化直接驱动表结构变化。

### 18. FastAPI 中间件和依赖项如何选择？

**回答：** 中间件适合对所有请求生效的横切逻辑，如 request ID、耗时、CORS 和通用日志。依赖项适合路由级且需要业务上下文的逻辑，如解析当前用户和权限。异常处理器负责把不同异常统一转换为响应。

### 19. 后台任务如何选择？

**回答：** FastAPI `BackgroundTasks` 适合发送日志、轻量通知等短任务，它与应用进程共存，没有可靠持久化。耗时、必须重试或不能丢失的任务，应使用 Celery、RQ、Dramatiq 等任务队列，或使用具备持久化工作流能力的系统。

### 20. 如何设计可靠重试？

**回答：** 只重试临时错误，并采用指数退避加随机抖动，设置最大次数和总截止时间。写操作必须先保证幂等。参数错误、权限错误等永久错误不应重试。超过次数后进入失败队列或人工处理，同时保留错误上下文。

### 21. Uvicorn 多 Worker 有什么作用？

**回答：** 单个 Worker 有一个事件循环，多 Worker 是多个进程，可以利用多核并隔离故障。进程之间不共享内存，因此会话、限流计数和任务状态不能只放在全局变量中，应放入 Redis 或数据库。Worker 数量要结合 CPU、内存、请求类型和压测决定。

## 三、鉴权、安全与多用户隔离

### 22. Authentication 和 Authorization 有什么区别？

**回答：** Authentication 回答“你是谁”，例如登录并验证 token；Authorization 回答“你能做什么”，例如普通用户不能访问管理员接口。认证成功不代表可以访问任意资源。

### 23. JWT 的结构和校验过程是什么？

**回答：** JWT 通常由 Header、Payload、Signature 三部分组成。Payload 只是 Base64URL 编码，并未加密，不能放密码等敏感信息。服务端需验证签名、算法、过期时间、签发者、受众等声明，然后再做权限和资源归属检查。

### 24. Access Token 和 Refresh Token 怎样设计？

**回答：** Access Token 生命周期短，用于访问接口；Refresh Token 生命周期长，只用于换取新 token。刷新时应支持轮换：每次使用后作废旧 Refresh Token，并记录 token family；发现旧 token 被再次使用时，撤销整组会话。

Web 场景可把 Refresh Token 放在 `HttpOnly + Secure + SameSite` Cookie 中，降低被脚本读取的风险。Access Token 放内存还是 Cookie，要结合 CSRF 防护和部署方式选择。

### 25. JWT 如何注销？

**回答：** 纯无状态 JWT 在过期前无法天然撤回。常用方案是短期 Access Token + 服务端保存 Refresh Token 会话；注销时撤销刷新会话，Access Token 等待短时间自然过期。高风险系统还可维护 `jti` 黑名单或用户 token version，但会引入状态查询。

### 26. RBAC 和 ABAC 有什么区别？

**回答：** RBAC 根据角色授予权限，简单易管；ABAC 根据用户、资源、动作和环境属性动态判断，更灵活但规则更复杂。项目初期可以用 RBAC 控制功能权限，再用资源归属条件保证用户只能访问自己的账单。

### 27. 如何实现用户数据隔离？

**回答：** 每张用户数据表保存 `user_id`，查询和更新都必须由后端从认证上下文注入 `user_id`，不能相信客户端传入的值。更新或删除使用 `WHERE id = ? AND user_id = ?`，返回 404 可避免泄露资源是否存在。还要为常用查询建立包含 `user_id` 的联合索引。

### 28. XSS、CSRF 和 SQL 注入分别如何防护？

**回答：**

- XSS：默认转义不可信内容，限制危险 HTML，使用 CSP，敏感 Cookie 设置 HttpOnly。
- CSRF：SameSite Cookie、CSRF Token，并校验 Origin/Referer；Bearer Token 若不由浏览器自动附带，风险模型不同。
- SQL 注入：使用参数化查询或 ORM 参数绑定，不能拼接用户输入；数据库账号遵守最小权限。

### 29. 密码应如何存储？

**回答：** 使用 Argon2id、bcrypt 等专用密码哈希算法，每个密码使用随机盐，并配置合适成本；不能明文存储，也不能只做普通 SHA 哈希。登录接口还需要限速、失败审计和防止账号枚举。

## 四、MySQL 与事务

### 30. 为什么数据库索引常用 B+ 树？

**回答：** B+ 树分支多、高度低，适合磁盘页；非叶子节点只存键和指针，单页能容纳更多索引项；叶子节点有序相连，范围查询高效。哈希索引适合等值查找，但不擅长范围和排序。

### 31. 聚簇索引和二级索引是什么？

**回答：** InnoDB 主键索引的叶子节点存整行数据，因此是聚簇索引；二级索引叶子节点通常保存索引列和主键。通过二级索引查未覆盖字段时，还需要按主键回到聚簇索引取数据，称为回表。

### 32. 联合索引的最左前缀原则是什么？

**回答：** 联合索引按列顺序排序，例如 `(user_id, created_at, id)` 可高效支持从 `user_id` 开始的条件以及之后的范围和排序。跳过最左列通常不能充分利用该索引。是否使用索引最终要看优化器和执行计划，不能只背规则。

### 33. 什么是覆盖索引？

**回答：** 查询需要的字段都可以从某个索引中获取，无需回表。它能减少随机 I/O，但索引列越多，存储和写入成本越高，不应为每条查询堆一个超宽索引。

### 34. ACID 分别是什么？

**回答：** 原子性保证事务内操作全成或全败；一致性表示事务使数据从一个合法状态到另一个合法状态；隔离性控制并发事务相互可见程度；持久性保证提交结果在故障后仍能恢复。数据库通过日志、锁和 MVCC 等机制共同实现这些性质。

### 35. 四种事务隔离级别是什么？

**回答：** 从弱到强通常是读未提交、读已提交、可重复读、串行化。它们依次解决脏读，并逐步限制不可重复读和幻读。隔离越强，并发能力通常越低。

MySQL InnoDB 默认常见配置是可重复读，并通过 MVCC 和必要的间隙/临键锁处理一致性读取与当前读问题。具体行为需要区分快照读和加锁读。

### 36. MVCC 如何工作？

**回答：** MVCC 为记录维护版本信息，通过 undo log 找到旧版本，事务根据 Read View 判断哪个版本可见。普通 `SELECT` 常使用一致性快照，读写之间减少互相阻塞；`SELECT ... FOR UPDATE` 等当前读会读取最新版本并加锁。

### 37. 什么情况下会发生死锁？如何处理？

**回答：** 多个事务以不同顺序持有并等待对方需要的锁，可能形成循环等待。应统一加锁顺序、缩短事务、建立合适索引以减少锁范围，并捕获死锁错误后对幂等事务做有限重试。不能靠把超时时间调大解决。

### 38. 什么是 N+1 查询？

**回答：** 先查一批主记录，再为每条记录各查一次关联数据，总查询数从 1 变成 N+1。可使用 JOIN、预加载或批量 `WHERE IN` 解决。优化前应关注结果集大小，避免一个 JOIN 产生巨量笛卡尔结果。

### 39. 一条慢 SQL 如何排查？

**回答：** 先用慢查询日志和 trace 确定 SQL 与实际耗时，再看 `EXPLAIN`/`EXPLAIN ANALYZE` 的扫描行数、索引、连接顺序、排序和临时表。之后判断是索引问题、SQL 写法、数据分布、锁等待还是连接池问题，并用真实数据验证优化效果。

## 五、Redis 与缓存

### 40. Redis 为什么快？

**回答：** 数据主要在内存中，数据结构针对常见操作优化；命令执行模型避免了大量共享数据加锁；I/O 多路复用可以处理大量连接。Redis 仍可能被大 Key、慢命令、网络、持久化和内存淘汰影响，不能简单理解为“所有操作都恒定很快”。

### 41. 常见 Redis 数据结构和场景有哪些？

- String：缓存对象、计数器、分布式锁的值。
- Hash：对象字段。
- List：简单队列，但可靠消息更适合 Stream 或专业消息系统。
- Set：去重、标签、共同关注。
- Sorted Set：排行榜、按时间或分值排序。
- Stream：消费组和可确认消息流。

### 42. Cache Aside 是什么？

**回答：** 读请求先查缓存，未命中则查数据库并回填；写请求先更新数据库，再删除缓存。删除而不是直接更新缓存可以减少并发覆盖和无效维护，但仍存在短暂不一致，需要结合过期时间、重试删除或消息通知达到业务需要的一致性。

### 43. 缓存穿透、击穿和雪崩有什么区别？

**回答：**

- 穿透：大量查询不存在的数据，缓存一直未命中。可做参数校验、缓存空值、布隆过滤器和限流。
- 击穿：一个热点 Key 失效，大量请求同时回源。可使用互斥重建、逻辑过期或提前刷新。
- 雪崩：大量 Key 同时失效或缓存整体不可用。可让过期时间加随机值、多级缓存、限流降级，并提高 Redis 可用性。

### 44. Redis 分布式锁需要注意什么？

**回答：** 获取锁使用带过期时间的原子 `SET key value NX PX`；value 使用唯一请求标识；释放时用 Lua 脚本先比对 value 再删除，防止误删别人的锁。还要考虑任务超过租期、GC 暂停、主从切换和网络分区。对强一致写入，数据库唯一约束、版本号或专门协调系统通常更可靠。

### 45. 如何用 Redis 保存会话和任务状态？

**回答：** 用不可猜测的 session/task ID 做键，值包含用户 ID、状态、版本和必要上下文，设置 TTL，并在每次读取时校验归属。长任务状态不能只依赖 Pub/Sub，因为订阅者离线时消息会丢失；需要恢复时使用 Stream、数据库或持久化任务队列。

## 六、SSE、WebSocket 与流式响应

### 46. SSE 和 WebSocket 如何选择？

| 维度 | SSE | WebSocket |
| --- | --- | --- |
| 通信方向 | 服务端到客户端单向 | 全双工 |
| 协议 | HTTP 长连接 | HTTP Upgrade 后使用 WebSocket 帧 |
| 浏览器能力 | `EventSource` 自动重连 | 需自行处理重连与协议 |
| 数据格式 | 文本事件 | 文本和二进制 |
| 适用场景 | 模型输出、通知、进度 | 聊天、协作、游戏、双向实时控制 |

AI 对话通常先选 SSE，因为主要流量方向是服务端向浏览器推 token，基础设施也更容易兼容。

### 47. SSE 生产环境要处理什么？

**回答：** 设置正确的 `Content-Type: text/event-stream`，定期发送心跳，禁用代理缓冲，处理断线和客户端取消，必要时使用事件 ID 恢复。服务端还要设置并发上限和超时，避免连接无限占用资源。

### 48. 什么是背压？

**回答：** 生产者生成速度超过消费者处理速度时，数据会不断堆积。可使用有界队列、暂停读取、批量发送、丢弃可丢事件或降低生成速率。若完全没有上限，慢客户端可能持续占用内存并拖垮服务。

### 49. 用户点击“停止生成”后，后端应做什么？

**回答：** 前端取消请求只是第一步。服务端要感知连接断开，取消当前协程，并尽可能取消上游模型请求；对已经调用的外部工具要定义可取消与不可取消边界。最后保存已生成内容和取消状态，避免任务一直显示“进行中”。

## 七、Node.js 与 NestJS

### 50. Node.js 为什么适合 BFF？

**回答：** Node.js 擅长 I/O 密集服务，TypeScript 类型可与前端共享，生态适合接口聚合、SSR、CLI 和工程工具。BFF 的主要工作通常是并发请求下游、转换数据和鉴权，而不是重 CPU 计算，因此与 Node.js 的事件循环模型匹配。

### 51. Node.js 事件循环的基本原理是什么？

**回答：** JavaScript 主线程执行回调；网络和部分系统操作交给操作系统或线程池；结果就绪后进入相应队列，再由事件循环调度。Promise 回调属于微任务，会在当前调用栈结束后、进入后续事件循环阶段前执行。大量同步计算仍会阻塞所有请求。

### 52. `process.nextTick`、Promise 和 `setTimeout` 的顺序是什么？

**回答：** 在 Node.js 中，当前调用栈结束后通常先清空 `process.nextTick` 队列，再处理 Promise 等微任务，然后进入定时器等事件循环阶段。具体输出还受运行上下文和 Node 版本影响。更重要的是避免递归堆积 `nextTick` 或微任务导致 I/O 饥饿。

### 53. NestJS 的 Module、Controller、Provider 是什么？

**回答：** Module 组织能力边界和依赖；Controller 接收请求并调用用例；Provider 通常承载服务、仓储或客户端，通过依赖注入获得。良好结构应让 Controller 保持薄，业务逻辑可独立测试。

### 54. NestJS 中 Middleware、Guard、Pipe、Interceptor、Filter 如何区分？

- Middleware：路由处理前的通用请求逻辑。
- Guard：决定请求是否允许进入，常用于认证授权。
- Pipe：参数转换和校验。
- Interceptor：调用前后增强，如响应包装、缓存、耗时和超时。
- Exception Filter：捕获异常并转换响应。

### 55. NestJS 的依赖注入有什么价值？

**回答：** 类声明自己需要的抽象，由容器负责创建和连接实例，从而降低模块耦合，并便于测试时替换数据库或外部 API。依赖注入不是自动消除耦合；如果 Service 直接依赖大量具体实现，结构仍然会变差。

### 56. BFF 聚合多个下游接口时如何提高可靠性？

**回答：** 独立请求并发执行；为每个下游设置超时和错误分类；关键数据失败则整体失败，非关键数据可降级；对临时错误做有限重试；使用熔断和限流保护系统；传递 trace ID。不能无条件 `Promise.all`，因为任一失败会直接拒绝，可根据业务使用 `Promise.allSettled` 并显式处理部分结果。

### 57. 什么时候用 Worker Threads 或子进程？

**回答：** 图片处理、压缩、复杂解析等 CPU 密集任务会阻塞事件循环，可交给 Worker Threads；需要更强隔离或运行其他程序时可使用子进程。普通数据库和 HTTP 请求不需要为了“并发”创建 Worker。

## 八、前后端协作与 React 数据层

### 58. 服务端状态和客户端状态有什么区别？

**回答：** 服务端状态来自远端，具有缓存、过期、并发更新和重试等问题，适合 TanStack Query 等工具；客户端状态是当前页面交互状态，如弹窗和筛选条件，适合组件状态或轻量状态库。把接口数据全部复制到全局 Store，会产生双份真相和同步问题。

### 59. 乐观更新如何实现？

**回答：** 发请求前保存旧缓存并立即更新 UI；失败时回滚；成功后用服务端结果校准或重新获取。涉及余额、库存等强约束数据时要谨慎，服务端仍是最终权威，并用版本号或幂等键处理并发。

### 60. SSR、CSR 和 Hydration 是什么？

**回答：** CSR 在浏览器生成主要页面；SSR 在服务端先生成 HTML，首屏和 SEO 较好；Hydration 是客户端 React 接管服务端 HTML 并绑定交互。服务端和客户端首次渲染结果不同会产生 hydration mismatch，常见原因包括随机值、时间、浏览器专属 API 和不一致数据。

### 61. CORS 是什么？

**回答：** CORS 是浏览器执行的跨源访问控制机制，服务端通过响应头声明允许哪些源、方法和请求头。某些非简单请求会先发送 OPTIONS 预检。CORS 不是服务端接口的身份认证，非浏览器客户端不受浏览器同源策略保护。

## 九、测试、可观测性与部署

### 62. 应该怎样设计测试层次？

**回答：** 业务规则使用快速单元测试；数据库仓储和外部边界使用集成测试；登录、创建账单、发起分析等关键路径使用少量端到端测试。不要用大量 E2E 覆盖所有分支，也不要只 mock 到无法发现真实接口问题。

### 63. FastAPI 项目重点测试什么？

**回答：** 权限和用户隔离、事务回滚、参数边界、幂等、缓存失效、外部模型超时、流式中断和任务重试。通过依赖覆盖替换数据库或当前用户，但关键集成测试应连接真实数据库和 Redis 容器。

### 64. 什么是日志、指标和 Trace？

**回答：** 日志记录离散事件和上下文；指标描述一段时间内的聚合趋势，如 QPS、错误率和延迟分位数；Trace 展示一次请求跨服务和外部调用的完整链路。三者通过 request/trace ID 关联，才能从告警快速定位具体请求。

### 65. 为什么看 P95/P99，而不只看平均延迟？

**回答：** 平均值会掩盖长尾。P95 表示 95% 的请求不超过该值，P99 更能反映少数用户遇到的慢请求。AI 服务还应拆分首 token 延迟、总生成时间、模型耗时、工具耗时和排队时间。

### 66. Docker 镜像如何优化？

**回答：** 使用小而明确的基础镜像、多阶段构建、锁定依赖、合理利用构建缓存，以非 root 用户运行，不把密钥打进镜像，并设置健康检查。容器应把状态放在外部存储，日志输出到标准输出供平台采集。

### 67. 服务如何优雅关闭？

**回答：** 收到终止信号后先停止接收新请求，再等待在途请求到设定期限，关闭数据库和 Redis 连接，保存或交接任务状态后退出。长连接和后台任务尤其需要明确关闭策略，否则发布时会丢消息或留下半完成任务。

### 68. 如何做一次有意义的压测？

**回答：** 先定义目标场景、并发模型和 SLO，再使用接近真实的数据与请求比例，逐级增加负载。记录吞吐、P50/P95/P99、错误率、CPU、内存、连接池和数据库慢查询。压测环境和依赖容量要说明，不能只报一个脱离条件的 QPS。

## 十、AI 应用工程

### 69. AI 应用为什么不能只做一次模型调用？

**回答：** 生产系统还需要身份与配额、输入校验、上下文管理、工具权限、结构化输出、超时重试、流式传输、成本统计、内容安全、评测和可观测性。模型只是系统中的一个不稳定外部依赖。

### 70. Agent Loop 的基本流程是什么？

**回答：** 将用户目标和工具描述交给模型；模型选择工具并生成结构化参数；程序校验参数、检查权限并执行工具；结果写回上下文；模型继续决策，直到给出最终答案或达到停止条件。必须设置最大步数、总超时、成本上限和重复调用检测。

### 71. Tool Calling 如何保证安全？

**回答：** 工具使用白名单和严格 Schema；服务端重新校验参数和权限；按用户注入数据范围；读写工具分级；高风险写操作增加确认和审计；工具结果作为不可信数据处理。模型只能选择预先注册的能力，不能直接执行任意代码或 SQL。

### 72. 如何防御 Prompt Injection？

**回答：** 不把外部内容当系统指令；明确区分指令与数据；敏感能力由代码权限控制而不是靠提示词；检索内容和工具输出做来源标记；最小化可用工具和凭证；对外部写操作增加策略校验。Prompt 本身不能构成安全边界。

### 73. AI 流式响应中如何保存消息？

**回答：** 先创建一条 `pending` 消息并获得 ID，流式增量可以只在内存或 Redis 中短暂累积，按时间或字符数批量持久化，完成后原子更新为 `completed`。失败或取消则保存已有内容和终止原因。这样可以恢复会话，也避免每个 token 都写数据库。

### 74. 如何评估 AI 功能？

**回答：** 建立包含正常、边界和对抗样本的固定数据集，定义任务成功率、工具选择正确率、参数正确率、事实性、延迟和成本等指标。自动评审适合规模化回归，但关键样本要人工抽检。每次修改 Prompt、模型或工具都跑相同评测集。

### 75. MCP 是什么？

**回答：** MCP 为模型应用连接工具、资源和提示提供统一协议，减少每个客户端与每个工具单独适配的成本。MCP Server 负责暴露能力，但认证、授权、输入校验和审计仍由实现者负责。用 TypeScript 编写 MCP Server 或 CLI，能很好体现 Node.js 工程能力。

## 十一、项目场景题

### 76. 如何介绍“消费分析助手”？

可以按 60 秒版本回答：

> 这是一个面向个人消费记录的 AI 分析应用。前端使用 React/TypeScript，后端使用 FastAPI，MySQL 保存用户、账单和分析记录，Redis 保存会话状态、热点统计和短期任务状态。用户登录后只能访问自己的数据，可以导入或维护账单，再通过 Agent Loop 调用统计工具完成分类汇总、趋势分析和自然语言解释。模型输出通过 SSE 流式返回。系统对工具参数做 Pydantic 校验，并设置超时、最大步数、幂等键和失败重试；日志通过 trace ID 串联接口、数据库和模型调用。

### 77. 为什么这个项目选择 FastAPI？

> 项目的核心能力包括数据分析、Agent 编排和模型调用，Python 生态更直接；同时请求大量等待数据库和模型 I/O，FastAPI 的 ASGI 与异步接口适合这类负载。Pydantic 还能统一校验接口和工具参数。若有面向多个前端的接口聚合，我会在外层增加 NestJS BFF，而不是把 AI 逻辑复制到 Node.js。

### 78. 如何保证用户 A 看不到用户 B 的账单？

> 登录后从已验证 token 得到 user ID。仓储层所有账单查询都强制带 user ID，更新和删除也使用 `id + user_id` 条件，不接受客户端指定数据归属。数据库对 `(user_id, created_at, id)` 建联合索引。接口层还通过 RBAC 控制管理能力，并写集成测试验证横向越权。

### 79. 模型接口超时怎么办？

> 我把连接超时、首 token 超时、总超时分开设置。未产生副作用的临时网络错误可以指数退避重试；工具写操作只有具备幂等键时才重试。达到上限后把消息标记为失败，保留已生成内容和 trace ID，前端提供重试入口。并通过指标区分排队、模型和工具耗时。

### 80. 如何实现会话恢复？

> MySQL 保存消息和最终状态，Redis 保存进行中的短期上下文与任务进度。客户端重连时携带会话 ID 和最后事件 ID；服务端先校验用户归属，再补发缺失事件或从已持久化内容恢复。只用进程内内存无法支持多 Worker、发布重启和故障恢复。

### 81. Redis 挂了，系统还能运行吗？

> 先按数据重要性区分。缓存不可用时，普通查询可限流后回源数据库；会话短期状态丢失时从持久化消息重建；分布式锁或限流依赖 Redis 的功能需要降级或暂时拒绝，不能假装成功。通过短超时、熔断和告警避免大量请求堆积。

### 82. 如果让 NestJS 做 BFF，边界怎么划？

> NestJS 负责验证前端会话、聚合用户资料和分析结果、转换字段、提供面向页面的接口，也可以代理 SSE。FastAPI 继续拥有消费分析、Agent 和数据规则。BFF 不直接跨过服务修改核心数据，服务间身份和 trace 信息显式传递，避免形成第二套业务逻辑。

### 83. 这个项目最值得讲的难点是什么？

推荐选一个真实做过的点，用“问题—约束—方案—结果—复盘”回答：

> 问题是流式生成过程中用户刷新页面后，消息容易丢失或永久停在生成中。约束是不能每个 token 都写 MySQL，也要支持多 Worker。我的方案是先创建 pending 消息，用 Redis 保存短期增量并按批次落库，完成、失败和取消都更新终态；客户端用事件 ID 重连。这样减少了写放大，也支持刷新恢复。后续还可以通过压测确定批量大小，并增加清理超时任务的定时任务。

### 84. 如何量化项目成果？

不要编数字。可以在本地压测后记录：

- 并发数、持续时间、请求分布和机器配置。
- P50/P95/P99、错误率、吞吐和首 token 延迟。
- 加缓存前后的数据库查询量和延迟。
- 串行与并行工具调用的总耗时。
- 异常注入后重试成功率和恢复时间。

简历写法示例：

> 通过并行执行无依赖分析工具，将固定测试集的平均分析耗时由 X 秒降至 Y 秒；使用 Redis 缓存高频统计结果，使相同压测条件下 MySQL 查询量下降 Z%。

## 十二、高频追问速答

### 85. 接口为什么要超时？

防止请求无限占用线程、连接和内存；总超时还应小于上游调用者的超时，给错误处理留时间。

### 86. 为什么重试要加随机抖动？

避免大量客户端在同一时间再次请求，形成重试风暴。

### 87. 为什么不能把 session 放在进程内存？

多 Worker 不共享内存，重启会丢失，负载均衡后请求也不一定落到同一进程。

### 88. 为什么数据库连接池不能越大越好？

连接会消耗服务端内存和调度资源；过多并发还会增加锁竞争。连接池应结合数据库上限、实例数和实际等待时间设置。

### 89. 什么时候使用消息队列？

需要异步解耦、削峰、可靠重试或事件广播时使用。引入后要处理重复消费、顺序、积压和可观测性。

### 90. 如何处理重复消费？

消费者以业务唯一键做幂等，使用唯一约束或状态机保证重复消息不会重复产生业务结果。

### 91. 限流算法有哪些？

固定窗口简单但有边界突发；滑动窗口更平滑；漏桶以稳定速率处理；令牌桶允许一定突发。实际选择取决于是否允许突发和限流维度。

### 92. 什么是熔断？

下游连续失败达到阈值后暂时快速失败，避免继续堆积；一段时间后半开探测，成功则恢复，失败则继续断开。

### 93. 数据库迁移如何安全上线？

使用向后兼容的扩展—迁移—收缩过程：先加新字段或表，让新旧代码都能工作；迁移数据并切流；确认无旧版本后再删除旧结构。

### 94. 为什么配置和密钥要分开？

普通配置可以进入版本管理，密钥应由环境或密钥管理系统注入，支持轮换和最小权限，避免出现在代码、镜像和日志中。
