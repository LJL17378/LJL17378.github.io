百度目前没有公开一套名为“全栈方向”的统一试卷。全栈候选人更可能进入前端、后端研发、AI 应用研发或业务研发的考试流程，因此准备选择题时不能只刷 JavaScript 语法，也不能完全照搬 Java 后端题库。

本文结合三类资料整理：

- [百度 2026 年 7 月 30 日后端研发岗公开回忆](https://onefly.top/zero2Leetcode/04_real_interviews/baidu/backend-20260730/)显示，当场为 15 道单选、5 道多选，并覆盖操作系统、数据库、网络、算法和大模型应用；
- 一份公开的[百度网盘前端面经](https://chenmijiang.github.io/Lao-Shang-Daily-Resources/2022/2022-12-15/%E7%99%BE%E5%BA%A6%E7%BD%91%E7%9B%98%E5%89%8D%E7%AB%AF%E9%9D%A2%E7%BB%8F.pdf)集中出现 JavaScript 类型、缓存、跨域、HTTP/2、事件循环、React、Node.js、构建工具和性能优化；
- 百度当前技术岗位要求仍明确强调数据结构与算法、操作系统、计算机网络和数据库等基础能力，可在[百度校园招聘岗位页](https://talent.baidu.com/jobs/)查看。

下面的题目分为两类：标注“公开回忆考点”的题目由公开资料中的考点改写；标注“扩展训练”的题目是按照同一能力范围设计的模拟题，不冒充百度原题。

## 应该怎样分配复习时间

| 模块 | 建议占比 | 需要达到的程度 |

| JavaScript / TypeScript / 浏览器 | 25% | 能推执行顺序、类型转换、缓存与跨域 |

选择题复习不是只记答案。每题至少要能说出：题干里的关键条件是什么、为什么正确选项成立、错误选项错在概念还是适用场景。

## 一、JavaScript、TypeScript 与浏览器

### 1. Promise 与微任务顺序（扩展训练，单选）

```javascript
console.log('A')
setTimeout(() => console.log('B'), 0)
Promise.resolve().then(() => console.log('C'))
queueMicrotask(() => console.log('D'))
console.log('E')
```

输出顺序是？

A. `A E C D B`  
B. `A C D E B`  
C. `A E B C D`  
D. `A E D C B`

**答案：A。**

同步代码先执行，因此先输出 `A、E`。`Promise.then` 和 `queueMicrotask` 都进入微任务队列，按入队先后输出 `C、D`。`setTimeout` 属于后续宏任务，最后输出 `B`。选择题常故意把“微任务优先”误写成“微任务会打断当前同步代码”，事实上必须先清空当前调用栈。

### 2. `typeof null`（公开前端考点，单选）

下列结果正确的是？

A. `typeof null === 'null'`  
B. `typeof null === 'object'`  
C. `null instanceof Object === true`  
D. `Object.prototype.toString.call(null) === '[object Object]'`

**答案：B。**

`typeof null` 返回 `object` 是 JavaScript 的历史遗留行为。`null` 不是对象，`null instanceof Object` 为 `false`；需要精确区分内建类型时，`Object.prototype.toString.call(null)` 返回 `[object Null]`。

### 3. `Object.is` 与严格相等（扩展训练，多选）

哪些表达式为 `true`？

A. `NaN === NaN`  
B. `Object.is(NaN, NaN)`  
C. `0 === -0`  
D. `Object.is(0, -0)`

**答案：B、C。**

严格相等认为 `NaN` 不等于自身，但把正零和负零视为相等。`Object.is` 恰好修正这两个特殊点：它认为 `NaN` 与自身相同，同时区分 `0` 和 `-0`。其他普通值上，两者通常表现一致。

### 4. TypeScript 的 `unknown`（扩展训练，单选）

关于 `unknown` 与 `any`，哪项正确？

A. `unknown` 可以不经检查直接访问任意属性  
B. `any` 比 `unknown` 更能保证类型安全  
C. 使用 `unknown` 前通常需要类型收窄  
D. `unknown` 只能保存对象，不能保存基本类型

**答案：C。**

两者都能接收任意值，但 `any` 会绕过大部分类型检查；`unknown` 在读取属性、调用或参与运算前必须先用 `typeof`、`instanceof`、判别字段或自定义类型守卫收窄。因此外部 JSON、异常值和第三方输入更适合先表示为 `unknown`。

### 5. CORS 预检（公开前端考点，多选）

哪些请求更可能触发浏览器的 CORS 预检？

A. 跨域 `POST`，`Content-Type: application/json`  
B. 跨域 `PUT` 请求  
C. 跨域 `GET`，只带简单请求头  
D. 跨域请求携带自定义头 `X-Trace-Id`

**答案：A、B、D。**

非简单方法、非简单请求头或非简单 `Content-Type` 会让浏览器先发 `OPTIONS`。普通简单 `GET` 可以直接发送实际请求，但响应仍需满足 CORS 头要求。预检是浏览器行为，不等于服务端真的执行了业务请求。

### 6. HTTP 缓存（公开前端考点，单选）

浏览器已有资源缓存，下一次请求携带 `If-None-Match`。服务端判断 ETag 未变化时，最合适的响应是？

A. `200` 并再次返回完整正文  
B. `204` 且删除本地缓存  
C. `304`，浏览器复用本地缓存正文  
D. `412`，表示资源不存在

**答案：C。**

ETag 用于协商缓存。资源未变化时返回 `304 Not Modified`，响应通常不带完整实体，浏览器继续使用缓存内容。强缓存命中时甚至不会向服务端发起这次验证请求；协商缓存则仍会产生网络往返。

## 二、React、Node.js 与工程化

### 7. React 列表的 `key`（扩展训练，单选）

为什么不建议在可插入、删除和重排的列表中使用数组下标作为 `key`？

A. React 禁止数字类型的 `key`  
B. 下标会让 JSX 无法编译  
C. 重排后同一个 `key` 可能对应不同业务项，造成状态错位  
D. 使用下标会强制组件进入服务端渲染

**答案：C。**

`key` 帮助 React 判断节点身份。列表重排后下标与业务项的对应关系改变，旧组件状态可能被错误复用到另一个项目。稳定且唯一的业务 ID 更能表达真实身份。静态、永不重排的列表使用下标通常不会出现这个问题。

### 8. Hooks 闭包（公开前端考点，单选）

某定时器回调总是读取到创建定时器那次渲染的旧 state，最准确的原因是？

A. React state 只能在 DOM 事件中读取  
B. 回调闭包捕获了当次渲染作用域中的值  
C. `setTimeout` 会把 state 自动转成字符串  
D. `useState` 更新是同步的，所以旧值覆盖了新值

**答案：B。**

每次渲染都创建自己的变量和函数。异步回调保留创建时的词法环境，所以可能看到旧值。解决方式要看目的：基于旧值更新可用函数式更新；需要持续读取最新值可同步到 `useRef`；副作用依赖某值则应正确填写依赖并处理清理。

### 9. Node.js 事件循环（公开前端考点，单选）

下列哪项最准确？

A. Node.js 中所有 JavaScript 回调都会同时在多个线程执行  
B. 事件循环适合协调大量 I/O，但 CPU 密集计算仍会阻塞主线程  
C. 使用 Promise 会自动把 CPU 计算放入线程池  
D. `async/await` 会为每个请求创建一个操作系统线程

**答案：B。**

Node.js 的 JavaScript 执行主线通常是单线程的，I/O 由操作系统或 libuv 协作，完成后再调度回调。Promise 和 `async/await` 改变异步代码组织方式，不会把普通 CPU 计算自动并行化。CPU 密集任务应考虑 Worker Threads、子进程或独立计算服务。

### 10. BFF 的职责（扩展训练，多选）

哪些工作适合放在面向前端的 BFF？

A. 聚合多个下游接口并转换为页面需要的数据形状  
B. 保存所有核心业务的唯一账本与最终一致性规则  
C. 统一处理当前客户端的鉴权上下文和错误映射  
D. 根据 Web、移动端差异裁剪字段

**答案：A、C、D。**

BFF 的价值是适配客户端：聚合、裁剪、协议转换和统一入口。核心领域状态不应只存在某个客户端专用层，否则多个渠道会出现规则分叉。BFF 可以校验身份并向下游传递可信上下文，但资源授权仍应由拥有数据的服务再次确认。

### 11. Tree Shaking（扩展训练，单选）

Tree Shaking 更依赖哪项条件？

A. 可静态分析的 ES Module 导入导出  
B. 运行时动态拼接所有模块路径  
C. 把所有文件包装进 `eval`  
D. 使用全局变量隐式注册模块

**答案：A。**

ES Module 的导入导出关系在编译期可分析，打包器能判断哪些导出未被使用。高度动态的 CommonJS 加载、`eval` 和隐式副作用都会降低静态分析能力。库还应正确声明副作用文件，避免样式或初始化代码被误删。

### 12. SSR 与 Hydration（扩展训练，单选）

服务端输出的 HTML 与客户端第一次渲染结构不一致，最可能造成什么？

A. 浏览器自动把 HTTP/1.1 升级为 HTTP/2  
B. Hydration mismatch，React 可能丢弃并重建部分 DOM  
C. 数据库事务自动回滚  
D. CSS 文件一定无法缓存

**答案：B。**

Hydration 要把客户端组件逻辑绑定到已有服务端 DOM。首屏结果不一致时，框架无法安全复用结构，可能报警并重新渲染。常见原因包括渲染阶段读取时间、随机数、只存在于浏览器的状态，或服务端与客户端使用不同初始数据。

## 三、网络、操作系统与 Linux

### 13. TCP 是字节流（公开笔试考点，多选）

关于 TCP，哪些说法正确？

A. 一次 `send` 必定对应接收端的一次 `read`  
B. 序号、确认与重传共同支持可靠传输  
C. 应用层协议需要自行定义消息边界  
D. TCP 通过 JSON 字段恢复丢失的数据

**答案：B、C。**

TCP 提供有序可靠的字节流，不保留应用层消息边界。一次写入可能被拆成多次读取，多次写入也可能一次读到，因此 HTTP、WebSocket 或自定义协议都要定义长度、分隔符或帧格式。重传依赖 TCP 机制，与负载是否为 JSON 无关。

### 14. HTTP 状态码排障（扩展训练，单选）

网关能够连接客户端，但在规定时间内没有收到上游服务响应，最符合的状态码是？

A. `401`  
B. `404`  
C. `502`  
D. `504`

**答案：D。**

`504 Gateway Timeout` 表示代理或网关等待上游超时。`502 Bad Gateway` 更偏向上游返回无效响应或连接异常；`503 Service Unavailable` 表示服务暂时不可用，常见于过载、维护或无可用实例。排障时要结合是哪一层产生状态码，而不是见到 5xx 就笼统说“服务内部错误”。

### 15. 进程与线程（公开笔试考点，单选）

同一进程中的多个线程通常如何共享资源？

A. 共享地址空间，但各自拥有栈和寄存器上下文  
B. 每个线程拥有完全独立的虚拟地址空间  
C. 不共享堆，因此不会发生数据竞争  
D. 线程之间只能通过网络套接字通信

**答案：A。**

同进程线程共享代码、堆和打开的部分进程资源，各自保留栈、寄存器与调度状态。共享内存提高通信效率，也带来竞态条件、可见性和原子性问题，因此需要锁、原子操作、消息传递或不可变数据等手段。

### 16. 可恢复缺页（公开笔试考点，单选）

进程访问的虚拟页尚未载入内存，内核完成调页和页表更新后，通常从哪里恢复？

A. 从 `main` 重新执行  
B. 跳过出错指令  
C. 重新执行触发缺页的访存指令  
D. 永久终止进程

**答案：C。**

可恢复缺页属于 fault。原访存尚未成功，内核补齐映射后应重新执行该指令。若访问地址本身非法、权限不允许或调页失败，才可能向进程发送信号并终止。

### 17. Linux 文件权限（公开笔试考点，单选）

文件权限为 `-rw-r-----`，某用户属于文件所属组但不是所有者。该用户通常具有：

A. 只读权限  
B. 读写权限  
C. 只执行权限  
D. 无权限

**答案：A。**

三组权限依次属于所有者、所属组和其他用户。这里所属组对应 `r--`。目录上的读、写、执行含义与普通文件不同：目录的执行权限决定能否穿越并访问其中条目，也应单独掌握。

## 四、MySQL、Redis 与后端接口

### 18. 不可重复读（公开笔试考点，单选）

事务 T1 两次读取同一行，期间 T2 提交了对该行的修改，T1 第二次读取结果发生变化。这是：

A. 脏读  
B. 不可重复读  
C. 幻读  
D. 死锁

**答案：B。**

不可重复读关注“同一行的值变化”。脏读是读到未提交数据；幻读强调同一范围条件下返回的行集合发生变化。面试和选择题中先看“是否提交”“同一行还是行集合”，可以快速区分。

### 19. 联合索引（公开笔试考点，多选）

查询如下：

```sql
SELECT id, amount
FROM orders
WHERE user_id = ? AND status = ?
ORDER BY create_time DESC
LIMIT 20;
```

哪些判断合理？

A. `(user_id, status, create_time)` 有机会同时支持过滤与排序  
B. 把 `create_time` 放首列一定更利于两个等值条件  
C. 是否成为覆盖索引还取决于查询所需列是否在索引里  
D. 低选择性的单列 `status` 索引收益可能有限

**答案：A、C、D。**

联合索引通常让等值条件在前、排序或范围列在后。把 `create_time` 放在首位后，后续 `user_id,status` 很难形成有效最左前缀。覆盖索引不是看 WHERE 条件是否齐全，而是看查询所需列能否全部由索引提供。

### 20. Redis 缓存击穿（扩展训练，单选）

一个热点 key 过期瞬间，大量请求同时回源数据库。最符合哪种问题？

A. 缓存穿透  
B. 缓存击穿  
C. 缓存雪崩一定只影响一个 key  
D. 主从脑裂

**答案：B。**

击穿是热点 key 失效导致并发回源，可用互斥重建、逻辑过期、请求合并等方法缓解。穿透是反复查询本就不存在的数据，可考虑空值缓存、布隆过滤器和参数校验；雪崩是大量 key 同时失效或缓存整体不可用。

### 21. JWT 与权限控制（扩展训练，多选）

哪些说法正确？

A. JWT 有合法签名就说明当前用户一定有权访问任意订单  
B. 服务端仍需校验签名、过期时间、签发方和受众等声明  
C. 资源级权限要结合当前用户与目标资源关系判断  
D. 敏感密钥适合直接放入 JWT Payload，方便客户端读取

**答案：B、C。**

JWT 解决的是令牌完整性和声明传递，不自动完成业务授权。合法用户仍可能越权访问别人的资源。Payload 默认只是编码而非加密，客户端能够读到，不应放密码、密钥等机密数据。

### 22. 幂等与重试（扩展训练，单选）

支付创建接口遇到客户端超时重试，防止重复扣款的更合理方案是？

A. 只把请求方法改成 `GET`  
B. 客户端每次重试生成新的订单号  
C. 使用业务幂等键，并在服务端原子地记录与复用处理结果  
D. 把超时时间改成无限长

**答案：C。**

网络超时不代表服务端没有执行。幂等键应在同一业务操作的重试中保持一致，服务端通过唯一约束、事务或原子存储保证只处理一次，并返回首次结果。HTTP 方法语义有帮助，但不能代替业务层去重。

## 五、AI 应用工程

### 23. RAG 引用了旧制度（公开笔试考点，单选）

检索结果相关度很高，但混入已经失效的制度版本。优先改进什么？

A. 提高 temperature 让模型自行融合  
B. 扩大 Top-K，把更多新旧文档一起交给模型  
C. 在召回和重排阶段加入版本、生效时间与来源过滤  
D. 缩短回答，减少用户发现错误的概率

**答案：C。**

根因是错误版本进入上下文，应在数据治理、元数据过滤和重排阶段解决。把互相冲突的版本一起交给生成模型，会把确定性规则变成概率判断，增加幻觉。回答还应保留来源与版本，便于审计。

### 24. Function Calling 的安全边界（公开笔试考点，单选）

模型输出了“退款”工具调用及参数，系统应如何处理？

A. 模型已经理解用户意图，直接执行  
B. 后端校验参数、身份、资源权限和业务状态后再执行  
C. 让模型自行查询数据库并写入退款记录  
D. 只检查 JSON 是否能解析，不需要业务校验

**答案：B。**

模型输出始终是不可信输入。结构化 Schema 只能保证形状，不能证明用户有权限，也不能保证订单状态允许退款。查询与退款这类有前置关系的工具还要由系统强制执行顺序，高风险操作应具备幂等、审计与人工复核机制。

### 25. 降低摘要幻觉（公开笔试考点，单选）

让模型总结工单且不得补充原文没有的事实，哪种约束更合适？

A. 信息缺失时明确输出“未提供”，并要求结论仅依据输入  
B. 提高随机性，生成更多可能背景  
C. 强制回答更长  
D. 让模型根据常识补齐原因

**答案：A。**

仅说“不要幻觉”通常过于抽象。更有效的做法是限定证据范围，为未知状态提供合法输出，并要求关键结论附来源。在工程上还应结合结构化输出、检索证据、字段校验和离线评测，而不是只依赖一句 Prompt。

### 26. SSE 与 WebSocket（扩展训练，多选）

关于 AI 对话流式输出，哪些说法合理？

A. SSE 基于 HTTP，适合服务端持续向浏览器推送文本事件  
B. WebSocket 更适合需要频繁双向实时消息的场景  
C. SSE 天然保证业务消息永久保存，断线后一定不会丢  
D. 无论选哪种协议，都要设计取消、超时、重连和重复消息处理

**答案：A、B、D。**

SSE 的模型简单，浏览器原生支持事件流，适合 LLM token、进度和通知；WebSocket 提供全双工通道，适合双向交互。传输协议本身不会替你完成业务持久化与精确一次投递，仍要设计事件 ID、断点续传、幂等和资源清理。

## 两周准备方案

### 第 1 至 3 天：JavaScript 与浏览器

复习类型判断、原型链、闭包、事件循环、Promise、模块、HTTP 缓存、Cookie、CORS。每天做 30 道选择题，并把错题改写成“条件变化后答案是否改变”的变式。

### 第 4 至 5 天：React、Node.js 与工程化

重点理解渲染与提交阶段、Hooks 闭包、列表协调、SSR/Hydration、Node.js 事件循环、流与背压、CommonJS/ESM、构建产物和 Tree Shaking。不要只背 API 名称。

### 第 6 至 8 天：计算机基础

按一次请求链路串联 DNS、TCP、TLS、HTTP、缓存、代理与状态码；按一次程序运行串联进程、线程、虚拟内存、系统调用、I/O 多路复用与文件权限。每个概念都准备一个故障现象。

### 第 9 至 11 天：数据库与后端

覆盖事务隔离、MVCC、索引、SQL 执行计划、Redis 缓存问题、JWT/RBAC、幂等、限流、超时与重试。练习从 SQL 和接口场景判断瓶颈，而不是只背定义。

### 第 12 天：AI 应用工程

复习 RAG 的切分、召回、重排、版本过滤与评测；理解 Function Calling 的 Schema、鉴权、幂等、审计和执行边界；熟悉 SSE、WebSocket、取消和失败重试。

### 第 13 至 14 天：整卷模拟

按“20 道选择题 + 2 至 3 道编程题”限时模拟。选择题先做定义明确的题，再做计算和多选；不确定的多选逐项判断，不靠“选项数量感觉”。模拟后只统计三类问题：概念不会、题干漏条件、计算或代码粗心，并按原因回炉。

如果目标是 React/TypeScript + Python/FastAPI + Node.js BFF 的 AI 全栈岗位，选择题优先级应是：JavaScript 与网络第一梯队，操作系统与数据库第二梯队，React/Node 工程化和 AI 工具安全作为区分度。这样既覆盖研发岗的通用基础，也能体现全栈与 AI 应用经历。
